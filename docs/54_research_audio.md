## 2. 先行研究

### 2.1 NeoForge / MC 1.21.1 の音実装実態

- **sounds.json**：`assets/<namespace>/sounds.json` がサウンドイベントの定義本体。各イベントは `subtitle`（翻訳キー——字幕 ON 時の表示名）と `sounds`（配列——複数指定でランダム選択。`name`・`stream`・`volume`・`pitch`・`weight`）を持つ。音声ファイルは `assets/<ns>/sounds/<path>.ogg`（Forge/NeoForge ドキュメント、Minecraft Wiki）
- **stream**：数秒を超える音（楽曲・長い環境音・music disc 系）は `stream: true` 必須——メモリに全読込しない代わりに同時再生は 4 インスタンス上限。短い SE は stream なしで同時多数可
- **mono/stereo の意味**：**モノラル（1ch）＝定位する**（距離減衰・方向がつく）。**ステレオ（2ch）＝定位しない**（音量一定——楽曲・非定位環境音向き）。定位させる音は mono で収録する設計義務
- **サウンドカテゴリ**：バニラの再生系統（MASTER/MUSIC/RECORD/WEATHER/BLOCKS/HOSTILE/NEUTRAL/PLAYERS/AMBIENT/VOICE/UI）——音量設定・字幕の系統分けに直結。MOD 独自 SE は適切な系統への割当が設計項目
- **SoundEvent 登録**：サーバー側で鳴らすには `SoundEvent` の登録が必要（`DeferredRegister`）。マルチではサーバー発火→クライアント再生。位置指定再生（blockpos/entity 追従）と非定位再生（プレイヤーに直接）の使い分け
- **環境音の仕組み**：バニラはバイオーム単位の ambient sound（addition/loop/mood 系）＋次元の環境楽曲。MOD 次元は biome 定義に ambient 音を持たせるか、独自 Tick 側で発火させる設計になる——**docs/19 はこの発火方式を確定する**（§2 実装規格の範囲）
- **BiomeMusic/楽曲差し替え**：次元の環境楽曲は「バニラ楽曲を国にいる間止めて独自楽曲を流す」設計が必要（TF 事例——下記）

### 2.2 次元 MOD の音楽先例

- **The Twilight Forest**：次元内では**バニラ楽曲を止め独自環境楽曲を常時流す**（v4.0.860「Adjusted music to always play whenever in the Twilight Forest」——ambient1〜5.ogg を stream でループ/ランダム再生）。さらに **music disc 9 枚を探索報酬として配置**（Rotch Gwylt・MrCompost 作曲——ダンジョン・井戸等に隠す「発見できる音楽」）。本作が「第2の黄昏の森」を目指す以上、**次元内独自楽曲の独占＋発見型の音楽報酬**は直接の先例
- **アンビエンス系 MOD との相性問題**：Dynamic Surroundings / AmbientSounds が MOD 次元で誤った音景を選ぶ既知問題（TF が洞窟判定され海中音が鳴る等——GitHub issue 実例）。**本作の環境音は外部 MOD のバイオーム推定に依存せず自己完結**で設計する（共存＝「相手の誤選択を防ぐ」ではなく「自前で全量を供給する」方向）
- **Aether / その他大型次元 MOD**：次元環境楽曲＋ボス曲の二層が定石。ボス曲は幕と同期させる仕組み（戦闘フェーズでトラック切替）が一般的

### 2.3 「静寂を演出する」先例

- **Minecraft バニラの深層/古代都市**：環境音を極端に減らし不気味な反響音だけを残す——「無い音」を怖さにするバニラ内先例。05 章の無音区間はこの延長の完全版
- **Silent Hill 系ホラー**：ラジオノイズ＝敵接近の音的予告（音が情報を担う系譜——本作の「気配」音・異物のかすれた音と同型）
- **Inside / Limbo**：環境音主導で BGM をほぼ置かない——「音楽が少ない世界」で一回の楽曲が劇的に効く設計。05 章の「救出で音が爆発的に戻る」はこの原理
- **Outer Wilds 等**：テーマ曲が場所と結びつく（各国探検家の楽器が合奏される設計）——章別テーマが「集まる」終章設計の先例

### 2.4 非言語・字幕と音のアクセシビリティ

- **XAG 106**（独自音響の字幕名）：導線上意味を持つ音は全て字幕名を持つ——45/04 §5.2 H-4・§6 #1 で正典化済み（登録範囲＝導線上意味を持つ SE に限定、無音区間は字幕も出さない）。docs/19 の責務は**登録表の完全性**（全 SE の ID・字幕名・カテゴリを漏れなく）
- **バニラ字幕の表記慣習**：「〈主体〉：〈動作〉」二項型は 18 §1.5.2 で確定済み。音の**方向語**（バニラは `<` `>` `^` で方位表示）は字幕システムが担う——本書は「方向が情報になる音（拍子・鐘・気配）」を定位（mono）収録の要件として落とす
- **多重化（45/04 §3.2）**：C6 聴覚は C7 字幕とペアでのみ算入可——音は常に「字幕名とセットで一系統」。音だけに依存する必須情報は禁止（H-1）

### 2.5 配信・楽曲の権利実務

- **配信収益化と楽曲権利**：自作未使用の楽曲・権利クリアな素材のみを同梱するのが MOD 配信の実務上の必須条件（Content ID 系の波紋防止）。素材サイト利用時はライセンス文面の保管を要
- **音楽生成アプリ連携（Issue #26・将来ワークストリーム）**：docs/19 側は「楽曲の要件表＋権利方針の枠」を先に確定し、生成基盤は #26 の成果として後から差し込める設計にする（本書では連携インターフェースのみ定義）
- **VTuber 配信での定石**：BGM 音量の推奨設定・クリップ映えする音の瞬間（無音→爆発的復帰等）は配信者向けの注意書きとして資産化できる

## 4. 設計原則（P-AU——全ユニット共通の思考の型）

- **P-AU-01 音は「棄てられたもの」の手触り**：全ての音は「かすれた・古い・途中で止められた」質感を帯びる。新しい・綺麗な音は演出上の例外（救出・復帰の瞬間）にのみ使い、だからこそ効く
- **P-AU-02 静寂は素材である**：無音・間・薄い残響を「何もない」ではなく設計対象として扱う（幕間の間・05 章の無音・救出前の静けさ）。音を削る判断も設計
- **P-AU-03 環境一次・装置二次**：音の導線も環境（構造・地形・情景）が一次。音だけで成立する新規導線を作らない（45/04 B-1 と同型）
- **P-AU-04 聞こえること＝実在**：本作の世界では「音が鳴る＝誰かに聞かれた」——05 章の聞き手規則をこの世界の音の形而上学として全編に通す（他章では暗黙のルールとして機能）
- **P-AU-05 数値は実装者が迷わない粒度まで**：音量・減衰・長さ・ループ構造・発火条件は全て表で定義。「雰囲気で」で終わる音指定は不可
- **P-AU-06 バニラの語彙を裏切らない**：バニラ SE の意味（鐘・音符ブロック・ポータル音等）を上書きしない。独自音は独自の場面に
- **P-AU-07 配信者が黙っても状況が読める**：30 秒基準の音版——重要な状態変化は音で予告される（拍子・鐘・気配・無音への転換）
- **P-AU-08 登録表の完全性**：導線上意味を持つ SE は全て登録表に ID・字幕名・トリガー・カテゴリを持つ。漏れは検証で拾う対象
- **P-AU-09 権利は設計の一部**：素材の出所・ライセンス・生成連携の境界を素材要件に組み込む（後から権利で落とす楽曲を生まない）
- **P-AU-10 正典の値を再定義しない**：拍子窓・幕規格・字幕型・拾得音質感など承認済み値は引用のみ。変更が必要なら要承認へ

- 5.4 救出後の存続扱い（16-U4-Q1 承認値の反映——救出後も聞き手規則が残る形）
