# 59 リスク台帳の調査基準（Issue #7）

> **役割**：Issue #7（リスク台帳 → 成果物 docs/42 リスク台帳）の制作・レビュー全エージェントが共有する物差し。リスク管理の先行手法（ゲーム開発・プロジェクト管理系）・MC MOD 特有の法的/依存リスク・正典制約（G-RR 群）・設計原則（P-RR 群）・棚卸し項目（H 群）・組版テンプレを集約する。制作側は本書と正典を読み、テンプレに従って執筆する。
>
> **Phase 0 制約**：実装コードを書かない。本フェーズの成果は「IP・スコープ・技術・工数・人手・配信・品質の各リスクを、評価・緩和・早期警告・発火トリガーまで運用可能な粒度で設計した台帳」。リスク管理の実運用（定期レビュー・行の追加/状態遷移）は継続工程として設計に含める。

## 1. 先行調査：リスク管理の手法

### 1.1 リスク記述の作法（ゲーム制作者の台帳実務——Jenn Sandercock 系）

- **良いリスク記述＝対策行動に直結する記述**：一般論的な不安（「開発が遅れるかも」）ではなく、原因の根源まで掘った記述（「配信者交渉が最長の不確定要素で、L3 実施日が読めない」）。なぜ負なのかを記述内で言明する。
- **if/then 構文**：「〈条件〉が起きたら、〈結果〉になる」で書くと、発火条件と被害が分離でき、兆候監視と緩和策の両方に使える。
- **制御不能リスクも台帳に入れる**：他社の類似作先行等、確率を下げられないリスクは「影響を小さくする緩和」か「発生時の対処計画（contingency）」を持つ。発生したときにその場で考えず、計画をそのまま実行するための記述。
- **現在リスク vs 目標リスク**：現状の評価点と、緩和策発動後に許容したい着地点の両方を持つ。緩和して残る「残存リスク」を明示する。

### 1.2 評価・優先順位の標準形

- **深刻度×発生確率のマトリクス**：2軸でスコア化し、ヒートマップで見る。スコア規則は評価前に固定する（見てから動かさない）。
- **分類（カテゴリ）**：技術・スコープ・工数/人手・法務/IP・外部依存・スケジュール・品質・コミュニティ等の系で分ける。分類は網羅の抜け漏れ検出にも使う。
- **リスク vs Issue（課題）**：まだ起きていない＝リスク（予防・緩和）、起きてしまった＝Issue（対処）。台帳は両方の行を持てるが、管理動作が違うことを明示する。
- **RAID 構造**：Risk（リスク）・Assumption（前提）・Issue（課題）・Dependency（依存）の4面。本作は「前提」（例：JEI 必須・NeoForge 1.21.1 固定）と「依存」（外部 MOD/ツール/人）をリスクと並記する方が実態に合う。

### 1.3 監視・早期警告・レビュー周期

- **早期警戒指標（early signals）**：発生を待たずに兆候で検出する指標——例「募集開始から2週で応募0件」「Issue #13 の PoC が予定を2週遅延」。各行に「何を見て発火と判定するか」のトリガーを持つ。
- **発火トリガーと緩和の接続**：兆候が出たら「どの緩和策を、誰が、どこへ記録して実行するか」を先に設計する。兆候→行動の結線が台帳の価値。
- **レビュー周期**：レンズ別に周期を決める（単独開発では週次自己点検＋フェーズ境界レビューが現実解）。レビューでやること＝新規行の追加・スコア再評価・状態遷移・緩和策の発火判定。
- **状態ライフサイクル**：特定（identified）→監視中（watching）→緩和中（mitigating）→発生（realized → Issue 化）→解消/退場（closed）。退場理由も記録する（リスクが消えた根拠）。
- **エスカレーション規則**：深刻度上位・発生確率上昇中の行はユーザー判断へ早期に上げる（本プロジェクトは面白さの最終決定権＝ユーザー——AGENTS.md）。

### 1.4 ゲーム開発特有のリスク類型

- **スコープ過大／機能膨張**：TF級MODは数年規模。対処＝垂直スライス方式・章を独立追加可能な構造（docs/00 §5 済）＋「追加しない」判断の記録。
- **80-20 の罠（P-VS-05 関連）**：最後の20%の研磨（演出・配信映え）に工数が集中し、タイムボックスを逸脱する。兆候＝仕上げ工程の見積超過反復。
- **楽しさ未検証**：「面白いか」は実プレイまで不明（docs/00 §5）——Phase 2 実プレイ検証と巻き戻し回路が緩和。
- **単独開発の属人化**：バス係数1。緩和＝設計ドキュメントの正典化（本リポジトリ自体が緩和策）＋台帳による判断の外在化。
- **作りながら技術が潰れる**：世界生成・ボスAI・個別層同期・マルチ同期の技術難度（docs/00 §5）——Issue #13 の PoC ゲートが緩和。

### 1.5 MC MOD 特有の法的・依存リスク

- **Minecraft EULA**：MOD の販売・収益化は禁止（自作 MOD の所有権は作者にあるが、販売不可・ゲーム本体の再配布不可）。本作は無償公開前提で抵触しないが、収益系の導入検討が出た場合は赤。
- **Modrinth/CurseForge のポリシー**：他者作の同梱・フォーク・帰属表示の義務（Content Disclosures）。jarJar 同梱（GeckoLib 等）はライセンス適合の確認が条件。
- **素材ライセンス**：フォント（OFL＝埋め込み可・再配布条件あり）、効果音/楽曲（CC0・SONNIS GDC パック・自作が本線——40-Q23 承認で本線は自作）。調達難時の緩和が行。
- **Mojang 没案機能との距離**：没案の利用自体は違法ではないが「Mojang 公式との混同」「商標的近似」は避ける設計。Issue #35 が調査担当——台帳は結果を受ける行を持つ。
- **依存エコシステム**：NeoForge 1.21.1 / Java 21 固定（ADR-0002）。JEI・Patchouli・GeckoLib の API 変更・保守停止は依存リスク。MC バージョンアップ追随は「追随しない」方針の明文化で緩和（スライス期は 1.21.1 固定のまま）。
- **コミュニティ/配信リスク**：ネタバレの早期拡散・誹謗・パクリ疑惑——限定招待の権利枠組み（41-U3-Q2）と公開計画（Issue #8）側で緩和、台帳は兆候監視行を持つ。

## 3. 設計原則（P-RR 群）

- **P-RR-01 対策に直結する記述**：各リスク行は「何が・なぜ負で・どの兆候で発火し・発火したら何をするか」まで書く。一般論の不安は行にしない。
- **P-RR-02 評価規則を先に固定**：深刻度×発生確率のスコア規則を台帳冒頭で定義し、行の追加・再評価はその規則で機械的に行う。
- **P-RR-03 兆候→行動の結線**：各行に早期警戒指標（トリガー）と発火時の緩和/対処計画を必須列にする。「発生してから考える」行を作らない。
- **P-RR-04 リスクと前提と依存を並記**：RAID 構造——リスクだけでなく「成り立ちの前提」「外部依存」も同じ監視対象として扱う（前提が崩れる＝リスク発生）。
- **P-RR-05 単独開発の外在化**：判断・兆候・緩和の記述は第三者（将来の自分・後続エージェント）が読んで実行できる粒度にする。記憶に残す運用を禁止。
- **P-RR-06 退場を設計する**：行は増やすだけでなく、解消条件と退場記録の列を持つ。死んだリスクの記録は判断履歴として残す。
- **P-RR-07 面白さ優先のスコア付け**：深刻度は「工数被害」だけでなく「主題装置・配信映え・体験品質への被害」も評価軸に含める（本作の価値は面白さ）。
- **P-RR-08 レビューを義務化する**：週次自己点検＋フェーズ境界（Issue 完了時・Phase 移行時）のレビュー契機を台帳運用として設計する。

## 制作上の注意

- **重複記述をしない**：docs/57 の設計代替・docs/41 §5.5 の失敗モード・docs/40 §7 の「外す項目」台帳は既に詳細設計済み——docs/42 は「行を持ち・接続先として参照する」形に留め、内容の再定義はしない（G-RR-03/05）。
- **台帳は読む人が動ける粒度で**：兆候の判定・緩和の発火は将来の自分（または後続エージェント）が機械的に判定できる表現にする（P-RR-05）。
- **既存行の尊重**：docs/40 §9・docs/41 §8.4 の既存行は承認済みの値——語彙・リードタイム値を変えず、行の形に整流して引き継ぐ（G-RR-02/04）。
