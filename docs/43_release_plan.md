### 0.2 対象範囲

- **実装の各論**——計測ロガー・パック製造・掲載 CI 等の実装は Issue #13 系・実装フェーズへ手渡す。

## 1. 公開段階設計

### 1.1 段構成の全体図

公開工程は以下の直列＋循環で構成する（先行慣行「内部テスト → 限定招待 → 公開アルファ → ベータ → リリース」——docs/60 §1.2——に本作の検証3層〔L2/L3——docs/41〕と章構造〔P-RL-01〕を重ねた形）：

```
（Phase 2 スライス工程：S0〜S5／M0〜M5——docs/40 §6.2-6.3）
   │
   ▼
段 A  L2 限定招待 ──────→ 段 B  L3 限定公開配信 ──→ 段 C 公開アルファ ──→ 段 D ベータ ──→ 段 E 正式リリース
（非公開・検証層）        （限定公開・検証層）         （alpha チャネル）     （beta チャネル）   （release チャネル）
   │                        │                        │                    │                │
   └──────── 判定入力を供給 ──┴─ docs/41 §10.2 ─→ G-3 可否判定        章追加リリースが    段 F 章追加リリース
                                                    → G-4 解禁判定        本段の駆動単位      （循環：正式後も継続）
```

- **段 A・B は公開ではなく検証の段**——しかし公開工程の列に含める理由は二つ：① L2/L3 の成果が公開アルファ可否判定の入力そのもの（docs/41 §10.2）であり、② L3 の限定公開運用が D-7 サーバーイベント主経路の雛形（docs/40 §9「限定招待運用＝D-7 の雛形」——P-RL-09）。段 A・B の実施運用の正本は docs/41 に留め、本書は段の位置づけと成果の消費のみを設計する。
- **段 C（公開アルファ）が公開の起点**——解禁判定（§2 G-4）を兼ね、以降は不特定多数が到達し得る領域になる。
- **段 F（章追加リリース）は循環段**——段 D（β期）の駆動単位として各章の公開を担い、正式リリース後もポストゲーム等の追加単位として継続する（P-RL-01）。

### 1.3 収録範囲の境界

各段の収録範囲は**スライス端到端（OP〜序〜第1章〜村〜帰還——40-Q1）を基準線**として定義する：

- **段 A・B・C＝スライス範囲そのもの**：アルファがスライス範囲を超える要素（スライス外台帳 docs/40 §7 の項目——第2〜5章・終章・響界・ポストゲーム・ボス再戦・名づけ派生等）を含まないことを境界とする。スライス内で実装済みの全要素（月下の小島・マルチ機構・配信モード config 等）はアルファに含む——「検証済みのものだけが出る」が境界規則（40-Q2 承認済みのマルチ実装は専用サーバー動作＝D-4⑤ の実演でもある）。
- **段 D＝スライス＋追加済み章の逐次拡大**：追加は 1 完成塊ずつ（§2.5 の公開判定を通ったもののみ）。
- **段 E＝全章収録**：収録下限は要承約 43-U1-Q6 の決裁に従う。
- **言語の境界**：スライス期の検証言語は日本語のみ（42-U2-Q1——英語版は Phase 4 で範囲確定）。公開アルファ時点の言語対応は正典未確定のため要承認 43-U3-Q7（§6.4——43-U1-Q2 を併合）とする。正式リリース時の言語範囲は Phase 4 の確定値に従う。

**記録先**：判定票は本書 §2 のゲート判定記録表へ追記（票の蓄積＝外在化——P-RL-06）。摘要を Issue #8 コメントへ、工程上の影響がある場合は STATE.md へ転記。リスク行の状態を動かす検出があれば docs/42 §3.4/§3.2 の経路で台帳側へ送る（本書でリスク行を起票しない——G-RL-14）。

### 2.9 判定保留・不可時の経路

- **保留**（入力欠測・前提未着地）：欠測・未着地の内容を判定票に明記し、揃った時点で同一ゲートを再判定。待機中も他工程の進行を止めない（docs/41 §8.4「判定保留中の工程」のモデルに準拠）。
- **不可**（公開形の見直しが必要な判定）：ユーザーへ選択肢を提示する。選択肢の枠組みは docs/40 §6.5 の外挿超過時選択肢（章規模削減・分割リリース・制作期間見直し）を公開工程側へ適用したもの——①章規模の削減（公開単位を小さく）②分割リリース（段を増やす・刻みを変える）③制作期間の見直し（公開時点の再設定）。正典・面白さの方向性に関わる見直しはユーザーのみが裁定する（docs/40 §5.4 ⑤正典層と同型——G-RL-12）。

### 3.5 バージョンチャネル運用（alpha/beta/release の使い分け）

両プラットフォームとも 3 段チャネルを持つ（Modrinth：`release`/`beta`/`alpha`、CF：Release/Beta/Alpha——docs/60 §1.1）。公開段階（§1）との対応を以下に固定する：

| 公開段階（§1） | 掲載チャネル | 規則 |
|---|---|---|
| L2 限定招待・L3 限定公開配信 | **プラットフォーム非掲載** | 招待パッケージは非公開配布（docs/41 §2.5——「D-5 構想の先行形」）。Modrinth/CF には一切上げない |
| 公開アルファ | `alpha` | 解禁判定の目安＝Modrinth 公開アルファ掲載（41-U1-Q10・41-U3-Q2——判定手順の正本は §2） |
| ベータ | `beta` | 章追加候補の安定化段・修正の事前検証に使用（§1 の段構成どおり） |
| 正式リリース | `release` | 完成した塊のみを出す（TF 慣行——「不完全な領域を出さない」docs/60 §1.2） |
| 章追加リリース | β期＝`beta`／正式リリース後＝`release` | 完成した章単位で掲載（P-RL-01）。掲載チャネルは §1.2 段表・G-5/G-7 の段モデルに従属——β期（段 D）の章追加版は `beta` チャネル直行で alpha 掲載を経由しない（43-U1-Q3 案A：初回の章追加掲載が新規掲載版の割当チャネル切替点） |

運用規則：
- **下位チャネルの内容にも未完領域を含めない**——alpha/beta は「段階の表示」であり、未完の章・壊れた領域を混ぜた掲載は行わない（docs/60 §1.2 の TF 慣行を規則化）。
- **「チャネル昇格」と「段遷移」を分離する**——本作は**段遷移型**を採用：新規掲載版の割当チャネルは初回の章追加掲載をもって `alpha`→`beta` に切替わり（43-U1-Q3 案A・G-5）、同一 build が alpha→beta を逐次通る昇格運用は行わない。release への切替は G-6 正式リリース化判定の通過時点——段間ゲートの判定記録を公開実施票に添付する（P-RL-04）。
- **同一版のチャネル不一致を禁止**——Modrinth で `alpha` の版を CF で Release に出さない（両チャネルの版・段表示を一致させる）。
- **緊急修正（ホットフィックス）**：セーブ破壊・進行不能級の欠陥が公開後に発見された場合、**当該版数体系の最下位単位を上げた修正版**（43-U2-Q2 の採用体系に従う——案A 採用時は `build`）を同一チャネルへ掲載する。発火条件＝修正版の §4.5 ゲート通過（緊急時もゲートを省略しない——ゲートは公開品質の担保であり例外を設けない）。記録＝公開実施票に「緊急修正」として種別を付記し、changelog の「修正」欄で症状と対処を書く。掲載頻度・ペースの設計（定期リリースか随時か）は段構成・スケジュール側（§1/§8）に従属する。

### 3.6 版数体系（TF 型 major.minor.build 準拠の検討）

正典に版数規則の記述はなく（棚卸し L-04）、TF の慣行 `{major}.{minor}.{build}` は比較基準として提示されているのみ（docs/60 §1.2）。複数案を比較する：

| 案 | 体系 | 利点 | 欠点 |
|---|---|---|---|
| **A：TF 型（推奨）** | `{major}.{minor}.{build}`——MC バージョンごとに並行系統を維持。アルファ〜ベータ期は `major=0`（`0.y.z`）、正式を `1.0.0` 起点、章追加・コンテンツ追加＝`minor`、修正＝`build` | ベンチマーク作と同一体系（docs/60 §1.2）。章追加＝minor が P-RL-01「章の刻みで世界が育つ」と一致。MC 系統別並行管理が §7 移植評価の結果反映（移植時に新系統を別立て）と整合 | major/minor の意味付けは独自運用（semver ではない）——changelog で意味を説明する必要 |
| B：semver 標準形 | `{major}.{minor}.{patch}`＋jar 名へ MC 版付記 | 汎用・ツール親和 | semver の「破壊的変更＝major」が章追加の刻みと直結しない——章追加が major にならないよう運用注記が要る。実質 A の読み替えに近い |
| C：章番号連動形 | `major=章番号` | 「何章まで入っているか」が版数から読める | 終章到達後の保守更新・修正で体系が破綻。アルファ期の表現が不自然（0 章？） |

**推奨＝案A**（要承認 **43-U2-Q2**・書き戻し先＝本節 §3.6）。jar ファイル命名は `understory-{mc_version}-{mod_version}.jar` 形を推奨（MC 系統の識別はファイル名側に持たせる——実装上の命名は Phase 1 で確定）。MC バージョン系統は現行 1.21.1 固定（42-U3-Q2・G-RL-08）で並行系統は1系統のみ——移植評価（§7）の結果に連動して系統追加を判断する。

### 3.8 変更履歴（changelog）規則

正典に changelog 規則の記述なし（棚卸し L-05）——以下を規則として設計する：

- **掲載面**：全バージョンに changelog を必須付記。Modrinth・CF・GitHub Releases の3系統で**同一原文**を使い回す（正本＝GitHub Releases の本文——「正のビルド置き場」D-3 引用。配置手順は §3.4 工程3）。
