### H-01 次元生成方式

- **実現性評価：高**
  - 根拠（API 実在・先行実績、P-TV-03/05）：次元登録はデータパック駆動——`data/<ns>/dimension_type/`・`data/<ns>/dimension/`・`data/<ns>/worldgen/noise_settings/` の JSON 定義、NeoForge では `DatapackBuiltinEntriesProvider`＋`RegistrySetBuilder` で datagen 可能（NeoForge commit ad6bf94——docs/56 §1.1）。地形生成は `minecraft:noise` ジェネレータ＋noise_settings JSON（`noise_router`・`surface_rule`・`spawn_target`）。バイオームは `worldgen/biome` JSON＋`MultiNoiseBiomeSource`/`FixedBiomeSource`/`TheEndBiomeSource` 型の決定論的配置。先行実績＝Twilight Forest（`TFDimensionData.java`：固定時刻・座標スケール・minY・ambientLight を JSON 定義、`bootstrapStem` で LevelStem 生成——1.21.1 NeoForge 継続リリース中。docs/21 §2・docs/56 §1.1）。1.21 のチャンク生成は `ChunkGenerationTask`/`GeneratingChunkMap`/`GenerationChunkHolder` へ分離されほぼ非同期化（`ChunkPyramid` がステップ依存管理——docs/56 §1.1）。
- **検証内容（PoC 仕様——Phase 1 タスク）**：
  - 作るもの：国次元の最小骨格。①`dimension_type` JSON（国の環境値：ambientLight・天空光・天井有無・minY/height 等——環礁ごとの環境光・空演出の個別制御は次元タイプの単一固定値ではなく別機構で担う設計を確認、docs/40 §4.2）②`dimension` JSON（LevelStem＝`minecraft:noise` ジェネレータ＋バイオームソース）③`noise_settings` JSON（PoC 段では最小の地形輪郭——海と島の原型。環礁本体の実装方式は H-07 の選択に従属）④`worldgen/biome` JSON 1 バイオーム（決定論配置——`FixedBiomeSource` またはカスタム BiomeSource）。
  - 動かし方：NeoForge MDK（ModDevGradle）1.21.1 で datagen（`DatapackBuiltinEntriesProvider`）により JSON を生成→統合サーバーで新規ワールドを作成→`/execute in` で次元へ移動し地形生成を確認。
  - 測るもの：①次元が LevelStem として登録・生成される（ワールド新規作成でエラーなくチャンクが埋まる）②noise_settings で地形輪郭（海/陸の原型）を制御できるか③バイオーム配置の決定性（座標→バイオームが安定）④`dimension_type` 各フィールドが環境表現に効くか（ambientLight・天空光・effects の視認確認——環礁別の個別制御の土台確認）⑤1.21 の非同期チャンク生成パイプラインで自前 noise が詰まり・エラーなく動作するか（`chunk_generation_stats`/ログ観測）。

### 7.2 同期計測：±100ms（H-16）

- **測定単位**：サーバー送出 tick・送出時刻と、各クライアントの再生開始時刻。LAN 2 人接続で N 回発火し、クライアント間の再生開始差の最大絶対値を jitter として集計する。

- **書き戻し導線**：実測値は docs/40 §4 の基盤要件・§5.2.2 T-7（マルチ共有イベント ±100ms 目標）へ着地として記録し、Issue #13 コメントまたは ADR に検証結果を残す（G-TV-12・P-TV-07）。

### 7.3 発生源位置の整合計測（H-17）

- **測定単位**：環境床・定位音の発火ログに記録される**発生源座標**と、正典構造アンカーの設計位置の差。
- **合格ライン**：発生源座標が設計位置と一致すること——03＝祭囃子の指揮台（`ambient.beat.bed` の発生源＝ボス）、04＝炉心最深部のボス位置（`ambient.forge.bed`＝最深部ボスの一打ちそのもの）（docs/19 §3.3・docs/16 §5（§5.3.4・§5.5.6）の構造アンカー）。
- **範囲の断り書き（横断監査指摘への対応）**：本節は **Issue #15 への引き継ぎ用の汎用規格**——検証環境には 03/04 環礁が存在せず、スライス内の床（序 `ambient.wave_raspy.bed`・01 `ambient.forest_moon.bed`）は stereo 非定位のため定位発生源の実材にならない。Phase 1 PoC では**合成定位源**（コードで発火点を固定した疑似定位床・mono 素材）で機構の成立のみを証明し、正典アンカーとの実座標整合は Issue #15 側（環礁設計確定後）で実施する。
- **書き戻し導線**：docs/19 §9→Issue #15 の手渡し項「各章の環境床・定位音の発生源位置を環礁設計の座標・構造と整合させる」の検証結果として、Issue #13 の検証記録から Issue #15 側へ座標整合の確認結果を引き継ぐ。

### 7.4 診断目標（暫定値の扱い）

- 送出 jitter の分解能指標として **±15ms** を置くが、これは**本計画の暫定診断目標であり正典値ではない**（正典の承認値は共有層音の同時配信 **±100ms**＝19-U4-Q4 のみ）。±15ms はログ計測の分解能・内部診断の目安として扱い、正典書き戻し・合格判定の対象にはしない。
- 生成負荷（ms/chunk・初期生成所要時間・TPS 影響）の閾値は暫定値とし、実測で確定して docs/40 §4 へ書き戻す（T-6——docs/40 §5.2.2「閾値は実測で確定」）。
