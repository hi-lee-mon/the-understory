# 71. Phase 0 設計書群の多観点レビュー——調査基準（Issue #1）

> **目的**：docs/00 レビュー工程に基づく Phase 0 全設計書の多観点レビューの**物差し**。完了条件＝全設計書へのレビュー指摘が「Issue 化または設計書反映」として記録されること。本作業は新規設計を書く工程ではなく、**設計品質の監査**である（G-RV-05）。

## 0. スコープ

- **対象**：docs/00〜docs/70 の全設計・技術・運用ドキュメント（調査系 docs/01〜08・21・22・33・35・37・39・47・49・53〜59・64〜69・71 は参照材料——レビュー対象は**正典として残る設計書群**：00・05・07・09〜20・23〜28・30_adr・32・34/・36・36a・38/・40〜46・48/・50〜52・60/61/62/63・67/・70/）
- **対象外**：実装コード（Phase 0＝設計のみ）・研究メモの文体品質
- **出力**：レビュー報告書 `docs/71_phase0_review_report.md`＋指摘台帳（severity＋処置区分＋推奨案つき）

## 1. 4観点と論点

### U1 ゲームデザイン（面白さ・一貫性）
- 「棄てられたものへの愛惜」「捨てる→届く→記録」の文法が全システムで一貫しているか（docs/23・32・14・16・38・45・63・67）
- 面白さ5系統（①愛惜と物語性②同席者配信③章＝エピソード④群像劇⑤沈黙と余白）の立ち方の系統チェック——各系統を担う書が齟齬なく束なっているか
- 機構の被覆：設計書間で定義が重複・衝突・欠落している機構（没腐・個別層・拾得・名付け・転移・境界）
- 数値系（docs/38）とシステム仕様（docs/32）・章設計（docs/34・16）の整合

### U2 物語（各章プロット・結末分岐）
- docs/34 各章プロット・docs/51 ボード・docs/12 ストーリー骨格・docs/28 フルフローの接続整合——結末分岐（綴じる/見届ける）と結末確定ルール（先着・共有層）の一貫性
- 伏線配置（docs/36・36a）の回収被覆——全断片に回収先があり孤立していないか
- キャラ（docs/25）・ロア断片（docs/52）・融合要素（docs/48）の物語上の役割と矛盾
- 要検討：物語の「穴」＝プレイヤーが答えを求めるのに設計が沈黙している箇所（設計的沈黙と単なる欠落の区別）

### U3 配信映え（クリップ性・エピソード構造）
- docs/70（台（台帳・イベント・観客参加）が docs/51・34・48 の実演出に被覆されているか——台帳 CM-ID と章ボード BD-ID の対応齟齬
- 30秒ルール・同席者方針・沈黙ポリシーの設計書横断の遵守状況
- 章＝エピソード構造の時間設計（docs/38 演出時間・docs/13 進行）と配信尺の整合
- 観戦/俯瞰不採用・配信モード差分の一貫適用

### U4 技術実現性（NeoForge 実装難度）
- ADR-0006〜0010 の前提と各設計書の齟齬——ADR 決定を暗黙に覆す設計記述の有無
- 先行ゲート（docs/57・40 §4.9）の前提行の着地状況——未着地前提を前提とする設計の棚卸し
- 個別層生成・可視性モデル・ワールド固定生成の設計書横断の技術整合（docs/16・32・40・57・30_adr）
- modpack 収録条件・性能閾値と設計が要求する負荷（docs/43・46・40 §4.8）

## 2. 正典制約（G-RV——全レビュー作業の強制条件）

- **G-RV-01**：指摘は必ず「どの設計書のどの節が・何と矛盾/欠落/破綻するか」を具体的に書く（曖昧な印象批評は指摘としない）
- **G-RV-02**：承認済み決定（要承認処理済み項・ADR Accepted）は覆さない——矛盾は決定のどちら側が書き換わるべきかの形で指摘
- **G-RV-03**：severity 3段階——`blocker`＝Phase 1 移行を止めるべき矛盾/欠落、`major`＝設計の意意図が損なわれる不整合、`minor`＝誤記・表現揺れ・軽微な抜け
- **G-RV-04**：各指摘に処置区分を付す——①設計書へ直接反映（誤記級）②Issue 化（設計変更級）③要承認（面白さの根幹——推奨案つき）④Issue 既存行への追記
- **G-RV-05**：レビューは監査——新しい設計案・新規コンテンツを提案しない。指摘は現行設計の修正に留める
- **G-RV-06**：全設計書に指摘を記録する義務はない——「問題なし」の判定も指摘と同格に扱う（被覆の証跡として台帳に残す）
- **G-RV-07**：日本語・Phase 0 制約（実装案を書かない）

## 3. 原則（P-RV）

- **P-RV-01**：正典参照優先——指摘の根拠は必ず正典（docs・ADR・承認済み項）に求め、「設計者の意図」の推測で断じない
- **P-RV-02**：1指摘＝1論点——複合問題は分割
- **P-RV-03**：severity 決定は影響ベース（Phase 1 着手可否・面白さの損壊・記録の揺れ）で判定
- **P-RV-04**：各書ごとに「監査済みマーク」を残す——未読の書がないことを台帳で証明する
- **P-RV-05**：要承認化の判定は「面白さの根幹・方向性・公開物」に限定（通常の修正級は要承認にしない）

## 4. 棚卸し（H-RV——レビュー対象の束ね）

- H-RV-01：正典設計書の一覧＝docs/ 直下の番号付きファイル群＋サブディレクトリ（34/・38/・45/・48/・51/・67/・70/）＋docs/30_adr/ 全 ADR——台帳で全件の監査済み状態を追跡する
- H-RV-02：承認済み決定の束ね＝各書の要承認集約（README §集約・§5/§8/§9 承認済み注記）＋ADR Accepted 一覧＋STATE.md の承認履歴——レビューの判定基線
- H-RV-03：条件付き改訂・未着地前提の束ね＝docs/42 §2 台帳＋docs/57 §8＋docs/40 §4.9 先行ゲート＋「Issue #15 着地」「Issue #13 検証」注記群
- H-RV-04：手渡し依存の束ね＝Issue #1 以外で未消費の手渡しコメント・書き戻し先
