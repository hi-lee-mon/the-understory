# 55 垂直スライス計画の調査基準（Issue #5）

> **役割**：Issue #5（docs/40 垂直スライス計画）の制作・レビュー全エージェントが共有する物差し。先行研究（垂直スライス方法論）・正典制約（G-VS 群）・設計原則（P-VS 群）・棚卸し項目（H 群）・組版テンプレを集約する。制作側は本書と正典を読み、テンプレに従って執筆する。

## 1. 先行研究：垂直スライスの方法論

### 1.1 定義と目的

垂直スライス（vertical slice）＝**ゲームの全レイヤー（技術・絵・音・遊び）を薄く切った「完成品質の一部分」**。水平に層を作る（全システムの骨格を先に作る）のではなく、縦に一本切り抜いて「最終品質の見本」を作る手法（ゲームデザイン標準用語——GDAD Wiki）。本作の採用理由は docs/00 の確定方針：「1章を最高品質で完成させてから量産」「面白いかは実プレイ検証」。

垂直スライスの目的は3つに整理される：

| 目的 | 内容 | 本作での対応 |
|---|---|---|
| **面白さの証明** | コア体験（ループ・感情曲線）が本当に面白いか実プレイで確かめる | 「没の掴み→拾得→待つ→救出→幕転換」の一連が第1章で成立するか |
| **品質基準の確立** | 後続章の量産基準（工数・素材要件・演出密度）を実物で示す | Phase 3 の章量産パイプラインの母型 |
| **リスクの早期摘出** | 技術・工数の詰みを量産前に潰す | 次元生成・環礁構造・多段ボス等の詰み要素を第1章で炙り出す |

### 1.2 スコーピングの作法（newgameplus.guide）

スコーピング＝**何を含め何を含まないかの決定**（見積もり＝所要時間の推定とは別工程と明確に分ける）。スライス計画書の二部構成が推奨される：

- **第1部＝体験の定義**：①ゲームプレイループ（プレイヤーが体験する一連を簡潔に記述）②クリエイティブ支柱（設計中常に意識する柱）③モーメント（プレイヤーに体験させたい瞬間——**全モーメントは支柱のどれかに紐付ける**。支柱はゲームを特別にするものなのでプレイヤーの眼前に置く）
- **第2部＝資産リスト**：作るべきものを資産種別にグループ化した to-do リスト（種別はジャンル依存——本作では構造物・モブ・アイテム・SE・楽曲・UI 器・演出イベント等に分類）

**含める/含まないの判定軸**：「その要素を抜くとコア体験の証明が壊れるか」——壊れるなら含める、壊れないなら切る（切ったものは台帳に残し後続フェーズへ受け渡す）。

### 1.3 よくある失敗（Wayline 2025）

| 失敗 | 内容 | 対策 |
|---|---|---|
| **速度の錯覚** | スライスの開発速度を全体開発速度に外挿してしまう | スライスは技術的負債・量産・バグ潰し・ローカライズ・プラットフォーム対応を含まない特例——速度を見積もりの根拠にしない |
| **過剰研磨** | 完成品質を目指すあまり全要素を丁寧に作り込み収束しない | 「good enough」を定義し研磨にタイムボックスを置く——**コア機能の証明が主、フィデリティは従** |
| **基盤の欠落** | 使い捨ての仕組みで作り量産時に作り直しになる | データ構造・パイプラインは量産前提の形で入れる（本格DBまでは要らないが「拡張できる構造」は必須） |
| **80/20の罠** | 最初の80%は速いが最後の20%が8割の時間を食う | スライス計画にもバッファを明示する |

### 1.4 Minecraft MOD の垂直スライス特性

- **検証経路が特殊**：市販ゲームのパブリッシャー向けスライスと違い、MOD はエンドユーザーへ直接届く。「誰に検証してもらうか」は配信者・テストプレイヤー（Discord 等）・自分たちの3層が現実解。
- **先行作の構成**：Twilight Forest は「次元＋章立て＋ボス＋進行ゲート」の完成形——**「章1本を作り切る」だけでも体験として成立する設計**を採っている（各章が独立した冒険単位）。本作はこの構成に「連続ドラマ（物語・選択の記憶）」を重ねた設計のため、スライスで検証すべきは**次元探索の面白さ＋物語装置の成立の両方**。
- **MOD 特有の検証項目**：マルチプレイ動作（LAN/サーバー）・競合互換性・配信実環境（コメント有りのプレイ）・modpack 収録前提の依存関係（JEI/Patchouli——Issue #22 確定）。

### 1.5 アクセシビリティ・配信観点

- XAG（Xbox Accessibility Guidelines）系の観点はスライス段階から入れる——後付けより計画時の方が安い。本作の a11y 設計は docs/45/04・Issue #34 が担当するため、スライス計画は「a11y 必須チャネルが実装対象に含まれる」ことを完了条件側で担保する。
- 配信映えはターゲット要件（docs/17）——スライスの「見せる瞬間」選定は**クリップ可能な瞬間**（章の幕開け・救出・結末）を含むべき。

## 4. 設計原則（P-VS 群）

- **P-VS-01 完走優先**：スライスは「短くても端から端まで遊べる」ことを最優先——途中で詰む・未完成要素で途切れる形は不可。
- **P-VS-02 主題装置は削らない**：面白さの識別子（没の掴み・拾得・語り・綴じ・選択の記憶）は量を減らしても機構としては必ず入れる。
- **P-VS-03 モーメント逆引き**：範囲は「プレイヤーに見せたい瞬間」から逆引きする——瞬間が成立しない要素は切る（newgameplus 作法）。
- **P-VS-04 拡張構造は作り捨てない**：データ構造・イベント配線・アセット規約は量産前提の形で入れる（使い捨てスライス禁止）。
- **P-VS-05 「good enough」の明文化**：各仕上げ領域に合格基準を置き、研磨はタイムボックス——「完成品質」の定義を数値・項目化しないと収束しない。
- **P-VS-06 検証は多層**：自分たちの到達確認→テストプレイヤー→配信環境、の3層で合格基準を分ける。
- **P-VS-07 切る判断は台帳に残す**：スライス外とした全項目は「いつ・なぜ・どこへ受け渡すか」を記録し後続工程の計画根拠にする。
- **P-VS-08 量産可否はスライスで判る**：スライスの所要工数から章量産の見通しを立てる——計画に「工数測定」を目的として含める。

## 6. 未決・要承認の想定枠（制作側へ）

- 序章・OP はスライスに含めるか（G-VS-01 は「第1章」を指定——序章の扱いを明確化する必要）
- マルチをスライス検証対象に含めるか（G-VS-08）
- 「完成品質」の定量化ライン（どこまで磨くか——P-VS-05）
- 外部テストの有無・方法（配信者・Discord・公開アルファ——Issue #22/#27 との関係）
- スライスに入る SE・楽曲の選別（docs/19 の素材から何を実装するか）
- 技術検証（Issue #13）とスライスの順序——先行検証か並走か
