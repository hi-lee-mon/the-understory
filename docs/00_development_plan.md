# 開発計画書 00：大型Minecraft MOD「第2の黄昏の森」

## 1. ビジョン

**「物語性・アクション・クラフトを備えた、黄昏の森に並ぶ世界観MOD」**を作る。ターゲットはYouTuber/VTuberとその視聴者。「配信されること」までを設計対象に含める。

## 2. 大方針：徹底的な設計

本プロジェクトの実行規範は**「設計→多観点レビュー→実装→多観点レビュー」**の反復（kakeiboプロジェクトで実績あり）。MODはゲームであり、「面白さ」はコード品質とは別に設計品質で決まる。よって：

- **設計フェーズを実装より重く**する（時間配分は設計6〜7割を想定）。
- 全設計は文書化し、**複数視点のレビューラウンド**を経てから実装に入る。
- 実装も「垂直スライス」から始め、1章を最高品質で完成させてから量産する。

### Phase 1：技術検証（Walking Skeleton）
- NeoForge 1.21.1 + Java 21 での開発環境・ビルド・CI。
- カスタム次元の生成（1バイオーム）、ポータル儀式、1モブ、1ボスの骨格。
- 「MODとして動く」ことを最速で証明し、設計の技術的前提を潰す。

#### Phase 1 拡張検証項目（Issue #25／署名演出の実現性）

| 項目 | 検証内容 | 現時点の見通し | 不可の場合の設計代替 |
|---|---|---|---|
| 異物の可視性モデル | 「発見した人にしか見えない」＝プレイヤー毎の表示差分 | ブロック単位の個人差分は困難と予想 | 「全員に見えるが初接触で消滅」（一期一会を物理成立）／エンティティ化して個別描画 |
| 個別化アイテム | 共有世界で「あなたが捨てた物」を所有者毎に表示 | ゴミ箱の所有者紐付け（ADR-0003）＋アイテムのname/lore個別化で概ね可能。ワールド状態分岐は不可（ADR-0004） | 表示のみ個別化・実体は共有 |
| 「色を取り戻す」演出 | 章浄化時の領域バイオーム再色付け | 1.18+は4x4x4セル単位のバイオーム置換が可能。ライブ更新の負荷が要検証 | フォグ/光源/パーティクル擬似着色で代替 |
| 「世界が壊れる」転調FX | カスタムポストエフェクト（テクスチャ乱れ・音逆再生） | バニラのポストチェーン機構は存在。Irisシェーダー併用時の共存は既知の難所 | フォグ・FOV・パーティクル・音響のみで擬似転調 |
| ゴミ箱転移の持ち込みルール | 次元移動の持ち込み可否ロジック | カスタム転移処理で実装可能と見通す。死亡時挙動・緊急脱出ハッチ化の防止ルールは要設計 | 持ち込み制限を撤廃して設計側で調整（ベッド儀式は削除済み） |
| カスタム和文フォント | 書物・語り形式の体裁に使うグリフ | フル漢字は数千字で制作/ライセンスコスト大 | かな＋頻出漢字サブセット、またはPixelMplus等のオープン和文ピクセルフォント |
| ボス演出基盤 | 多段変形ボスの標準構成 | GeckoLib＋Blockbenchが定石 | バニラ式の状態遷移で簡略化 |
| 環礁生成パフォーマンス | 大規模構造物＋空中環礁群の生成負荷 | 要実測（構造物分割・遅延生成が候補） | 環礁サイズ縮小・事前生成領域の限定 |

## 4. レビュー工程（kakeibo方式の踏襲）

設計・実装ともに**複数視点のレビュアーで複数ラウンド**回す：

| レビュアー視点 | 見るもの |
|---|---|
| ゲームデザイン | 設計原則（01）との整合・難度・報酬・創発性 |
| 世界観/物語 | 一貫性・テーマ深度・キャラ魅力・ロア品質 |
| 配信適性 | 章構造・クリップ可能性・マスコット・マルチ適性 |
| 技術 | 実現性・パフォーマンス・データ構造・拡張性 |
| 制作現実性 | 工数・スコープ・依存関係・リスク |

各ラウンドで blocker/major/minor を分類し、blocker/major ゼロで accepted。

## 5. 主要リスクと対策

| リスク | 対策 |
|---|---|
| スコープ過大（TF級は数年規模） | 垂直スライス方式、章を独立追加可能な構造に |
| 「面白いか」は実際に作るまで不明 | Phase 2 で第1章を実プレイ検証、面白くなければ仕様を巻き戻す |
| 世界生成・ボスAIの技術難度 | Phase 1 で技術検証、特に案C/Dの二層世界・時間操作は検証必須 |
| ローカライズ・演出工数 | 設計時点でテキスト量・演出量を見積もり対象化 |
| マルチプレイ同期 | ボス・ギミックのサーバー同期をPhase 1で検証 |
