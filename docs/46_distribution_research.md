| 領域 | 結論 | 提案 |

## 2. レシピ可視化：JEI / EMI / REI

### 2.1 現状の勢力図（2025-2026）

| MOD | 位置づけ | NeoForge 1.21.1 | 備考 |
|---|---|---|---|
| **JEI** | NeoForge 系の事実上の標準レシピビューア | 対応済み | 大部分の NeoForge パックに入る。MOD作者は `jei-api` にプラグイン実装 |
| **EMI** | 新しいレシピビューア（Fabric 出自→全ローダ対応） | 対応済み | 起動時のレシピ索引が並列で速い（大パックで有利）。**JEMI**＝JEI 併存時に JEI プラグインを EMI へ橋渡しする実行時互換を内蔵 |
| TMRV | JEI プラグインを EMI 上で動かす互換層（JEI 本体不要） | — | 「JEI を入れずに JEI 対応を走らせる」選択肢。整備者依存の中規模MOD |
| REI | Fabric 系の標準 | NeoForge は対象外 | 本作（NeoForge 専）では対象外でよい |

### 2.2 本作への含意

- **拾得鍛錬がクラフト主体**（docs/14）——レシピが見えない MOD は実質遊べない（M6 指摘そのまま）
- **通常のクラフトレシピ（JSON データパック形式）なら JEI が自動で索引**に入れる。追加実装はほぼ不要
- **独自機構がある場合**（例：拾得鍛錬台の「鍛錬」が専用 UI なら）、JEI カスタムカテゴリの実装が必要になる
- **EMI 対応は JEI 実装で実質カバー**（JEMI が実行時に橋渡し）。別途 EMI プラグインを書くのは余力があればの二次対応
- ゴミ箱の「返礼レシピ配達」等、**意図的にレシピを隠す場面**（招待状の手順）は JEI の表示/非表示制御の設計論点になる（見せるとネタバレになり得る）

## 3. ゲーム内ガイド：Patchouli

### 3.1 概要

- Vazkii 系の**ゲーム内ガイドブック標準MOD**（Botania の Lexica Botania の方式を一般化したもの）
- **1.21.1 から MinecraftForge を捨て NeoForge 専**——本作の技術選定（ADR-0002）と完全に一致
- **JSON データパック駆動**：`data/<ns>/patchouli_books/<book_id>/book.json`＋`assets/.../entries/` に頁を置くだけで本が作れる。**独自画面・独自コード不要**
- 実績連動で「読める頁」をロック解除できる（＝物語進行に連動した図鑑解放ができる）
- 翻訳（リソースパックの言語ファイル）、マルチブロック構造物の「幽体投影」プレビューにも対応

### 3.2 本作との一致度

| 本作の世界観 | Patchouli でできること |
|---|---|
| 書物・頁・綴じ目（docs/09・26） | 「拾い人の手記」「拾得図鑑」そのものをゲーム内書物として実装 |
| 拾った由来物を「図鑑に綴じる」体験（docs/14 §図鑑） | 実績ロック解除で拾得品の頁が増える＝「図鑑を育てる」 |
| 語りを文字の補助層に限定（Issue #31 で確定） | Patchouli = 読みたい人だけ開く任意の書物——「主線は非言語」と矛盾しない |
| 没案・断片のロア断片（docs/26） | 章ごとに頁を開放する形式と一致 |

### 3.3 採否の比較

| | 評価 |
|---|---|
| Patchouli 採用 | 実装コスト≈JSON記述のみ・標準UI・世界観一致・MODプレイヤーに既知。**推奨案** |
| 自前ガイド画面 | 独自表現は自由だが、UI実装・保守が重い。Phase 0 の方針「UI構造は変えない」ともズレる |
| 採用時の依存形態 | **soft dependency**（無くても本編は遊べる・あれば図鑑が出る）にして必須依存を増やさない（§4 の収録条件と整合） |

## 4. modpack 慣習と収録条件

### 4.1 基本構造：パックは自プラットフォームのファイルしか引けない

- **CurseForge パック**：CurseForge アプリ経由で CF ホストのファイルのみ（外部MODは「承認済み第三者リスト」入りが必要）
- **Modrinth パック（.mrpack）**：参照URLがホワイトリスト制——`cdn.modrinth.com` / `github.com` / `raw.githubusercontent.com` / `gitlab.com` のみ
- **⇒ 片方にしか置かない MOD はもう片方のパックに入らない**。「両方公開」が流通の必要条件

### 4.2 収録されるための実務条件

| 条件 | 内容 |
|---|---|
| ライセンス | **modpack への同梱を許可**する旨が明確なライセンス（ARR のままだと個別許諾が要り実質死ぬ）。Modrinth では SPDX 識別子必須 |
| config | デフォルト値がそのまま遊べること・サーバー向けに重要な値が外部config化されていること |
| 性能 | 大規模パックで重いMODは外される。次元追加MODは生成コスト・tick コストの予算が求められる |
| 依存 | 必須依存が少ないほど採用されやすい（JEI/Patchouli は optional 化が望ましい） |
| サーバー | **専用サーバーで動くこと**が次元MODの必須要件（イベント鯖・マルチで使えなければ配信経路が断たれる） |
| メタデータ | アイコン・説明文・カテゴリ・タグが整っていないと検索に載らない |

## 5. 配布チャネル戦略（推奨）

| チャネル | 役割 |
|---|---|
| **Modrinth** | 現行コミュニティ標準。検索性・ページ品質・APIが良い。**第一公開先** |
| **CurseForge** | 従来最大の流通基盤。**CF パックに入るために必須** |
| **GitHub Releases** | ソース公開・mrpack の参照元・技術ユーザー向け |
| **公式軽量パック（新設提案）** | 本体＋JEI＋Patchouli＋前提MODだけの最小パックを .mrpack / CF 両形式で出す→配信者・サーバー運営が**ワンクリック導入**できる形 |

## 6. 配信者への実際の到達経路

### 6.1 実績形式（日本の現状）

- VTuber の MOD マイクラ実績は、**個人の単体MOD遊びではなく「MOD入りカスタムサーバー／イベント」**が主形式
- 例：**ぶいきゃす（v-cas.com）**は 2025-12 に「ぶいきゃすマイクラ ドラゴンサバイバル」（複数MOD導入マルチサーバー、35名のVTuber、レンタルサーバーGMOペパボ提供）を主催——本作のターゲット層（YouTuber/VTuber）に完全に合致する形式
- レンタルサーバーのワンクリック導入は **CurseForge 由来**が主流——CF 公開がサーバー導線に直結

### 6.2 本作が取るべき経路

1. **公式軽量パックの整備**（§5）——「導入が一発」でなければイベント運営が採用しない
2. **サーバー運用可能なデフォルト値**——マルチ前提（docs/32 §6、docs/17 §1-2 と整合）・個人差分/共有村の初期値がイベント向きであること
3. **配信者向け素材**——docs/17 §7（世界観紹介・サムネ・導入手順・シェーダー推奨設定）を成果物として整備。導入手順は「パックを入れるだけ」まで下げる
4. **パック作者・イベント運営へのアプローチ**——収録条件を満たした上で、イベント向けの「期間限定没素材」余地（docs/17 §6）をアピール材料に
