# docs/68 技術ADR追加 調査基準（Issue #12）

## §0 目的・所掌

Issue #12「[技術] ADR追加：次元生成・セーブ/同期・マルチ・パフォーマンス」の物差し。**docs/30_adr/ に ADR-0006〜0009 を追加**し、既に承認済みの技術判断を「なぜそう決めたか」の決定記録として束ねる。

所掌：

- ADR-0006：次元生成方式（環礁本体＝案C ハイブリッド・異物チャンク＝案C・ワールド固定レイアウト・構造生成4型との関係）
- ADR-0007：セーブ・状態同期（共有層/個別層の永続化構造——ADR-0004 の技術実装側の記録）
- ADR-0008：マルチプレイ仕様（共有/個別の配信モデル・同期精度・見え方の差分）
- ADR-0009：パフォーマンス方針（暫定閾値・計測規格・互換検証・フォールバック構造）
- `docs/30_adr/README.md` の「既存ADR」一覧更新

所掌外：

- 既存 ADR-0001〜0005 の本文改訂（immutable——触らない）
- docs/57 の承認済み決定の再審議（引用・束ねるのみ）
- LICENSE（43-U2-Q1）の ADR 化判断——要否自体を要承認に
- Phase 1 スパイクで確定待ちの値（57-U2-Q8 近接範囲・57-U4-Q7 ダッキング量等）——ADR には「暫定・PoC で着地」と記す

## §1 前提・位置づけ

- ADR 規則（docs/30_adr/README.md）：`NNNN_タイトル.md` 連番4桁・immutable・1ADR=1決定・テンプレ＝Status/Date/Deciders/Related + Context/Decision/Alternatives/Consequences
- Status は **Proposed** で作成（Accepted 化＝ユーザー承認後——ADR-0002 の前例どおり）
- Deciders: `65banseki + Devin`／Date: `2026-10-25`
- Issue #12 への手渡し入力：docs/40 §4.7（データ構造一覧）・docs/57 §9.2（方式選択の ADR 化）・docs/42 §5.2（ADR 化トリガ規則）・docs/43（LICENSE・移植評価の ADR 化候補）

## §2 正典制約（G-ADR）

- **G-ADR-01**：正典値（承認済み決定・数値・ID・名称）は引用のみ・再定義禁止。変更が必要なら要承認へ
- **G-ADR-02**：承認済み決定を勝手に覆さない。ADR の Decision は「承認済み決定の束ね」で、新規の審美判断・仕様創作を Decision に混ぜない
- **G-ADR-03**：ADR-0004（物語/村共有＋個人差分個別）は上位決定——ADR-0007/0008 はその技術実装側の記録であり、矛盾する選択肢を採用しない
- **G-ADR-04**：Phase 0＝設計のみ。実装コード・JSON・クラス名の確定を Decision に書かない（方式・構造・責務の分割まで）
- **G-ADR-05**：未確定値（スパイクで着地する数値・方式の条件付き項）を確定済みのように書かない——「暫定値＋着地先」を明示
- **G-ADR-06**：条件付き確定項（57-U2-Q11——H-06 の案選択で発動する正典改訂連鎖）は Consequences に条件付きで記す（確定扱いしない）
- **G-ADR-07**：1ADR=1決定。4領域を1本にまとめない（README 規則どおり）。ただし ADR 間の前提・依存関係は Related/Consequences で相互接続
- **G-ADR-08**：Alternatives には「検討して却下した案＋却下理由」を実在の検討経緯（docs/57 の複数案比較・ADR-0002/0003 の判断史）から書く——創作の代替案を並べない
- **G-ADR-09**：日本語で書く・コード識別子は英語（AGENTS.md）
- **G-ADR-10**：Issue #13 完了条件の「検証結果を ADR に記録」は Phase 1 実施後——本 ADR 群は「検証前の設計決定記録」であり、実測結果の記録欄として Results 節は増やさない（Consequences に検証計画への接続を書く）

## §3 原則（P-ADR）

- **P-ADR-01**：Decision には採用決定の正典出典（57-U{n}-Q{m}・40-Q{n}・docs/NN §X）を必ず明記——「いつ誰に承認されたか」が追えること
- **P-ADR-02**：Consequences は良い面・悪い面・今後の制約の3層で書く（テンプレどおり）。特に「この決定が Phase 1 スパイクに課す合格条件」は必須
- **P-ADR-03**：4 ADR は相互に Related で接続（生成方式→個別層生成→セーブ構造→マルチ配信の連鎖）。README 索引にも依存関係を短く添える
- **P-ADR-04**：曖昧さの解消に挑む——「個別層が動いたとは何を指すか」「マルチで誰に何が見えるか」の判定可能な言語化を Decision に持たせる
- **P-ADR-05**：要承認は open_questions に集約し `12-U{n}-Q{m}` で採番（推奨案＋書き戻し先必須）。本文側は参照IDで示す
- **P-ADR-06**：ADR 群の成果物は docs/30_adr/ 直下（サブディレクトリを作らない）。README の既存 ADR 一覧に4行追加するのは成果物の一部（書き戻しではない）

## §5 組版テンプレ

各 ADR は docs/30_adr/README.md のテンプレに従う：

```markdown
# ADR-NNNN: タイトル

- Status: Proposed
- Date: 2026-10-25
- Deciders: 65banseki + Devin
- Related: （正典節・他ADR）

## Context
（なぜこの決定が必要だったか——設計書群でどこが未定義/暗黙だったか）

## Decision
（採用決定の言語化——承認済み正典の出典 ID を明記。暫定項は「暫定・着地先」を明記）

## Alternatives Considered
（検討して却下した案＋却下理由——実在の検討経緯から）

## Consequences
（良い面・悪い面・今後の制約＋Phase 1 スパイクへの合格条件・条件付き発動項・他ADRへの依存）

## Open Questions（要承認——`12-U{n}-Q{m}` 参照表）
```

出力は複数ファイルの場合 `=== FILE: docs/30_adr/NNNN_xxx.md ===` 区切り。
