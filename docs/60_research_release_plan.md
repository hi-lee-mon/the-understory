# docs/60 — リリース計画の調査基準（Issue #8 向け）

## 0. 位置づけ

- **本書の役割**：docs/43 の設計のための共通基準。docs/43 自体は「誰に・いつ・どう届けるか」の唯一の計画書

## 1. 先行調査

### 1.1 配布プラットフォームの仕様（一次情報）

**Modrinth**（公式ドキュメント）：
- バージョンチャネル3段：`release`（安定版）・`beta`（プレビュー）・`alpha`（初期/実験的）——ユーザーはチャネルでフィルタ可
- 環境タイプ：`client_and_server`・`client_only`・`dedicated_server_only` 等——本作は専用サーバー動作必須（D-4 収録条件）のため `client_and_server`
- ファイル上限 500 MiB、重複ハッシュの禁止、依存関係の宣言（required/optional/incompatible/embedded）
- modpack（.mrpack）：参照 URL のホワイトリスト制——**Modrinth 掲載外の MOD は .mrpack に入らない**（docs/46 §4.1）
- プロジェクト作成時にアイコン（256KB 以下 PNG/JPEG）・説明文・ライセンス識別子（SPDX）が必須
- **モデレーション審査**：審査の有無・期間とも一次情報未確認（暫定——docs/42 R-42）。公開アルファの掲載申請（docs/43 §8 8-G）時に公式ドキュメントで確認し、確認結果（審査の有無・実績期間・出典 URL）を本節へ追記する（Issue #8 43-U4-Q10 案A 承認・2026-10-06）

**CurseForge**（公式ブログ・審査ガイド）：
- モデレーション審査あり——パックは **CF ホストの MOD のみ**収録可（docs/46 §4.2）
- CF 公開はレンタルサーバー（ロリポップ等）のワンクリック導入に直結——サーバーイベント経路（D-7）の基盤
- バージョンチャネル：Release/Beta/Alpha の3段

**両公開の構造的必要条件**（docs/46 §4.1——承認済み D-3）：CF パックは CF ホスト限定、Modrinth パックはホワイトリスト制のため、片方のみの公開はもう片方のパックに入らない。

### 1.2 成功作のリリース慣行

**The Twilight Forest**（目標作——ベンチマーク）：
- 版数体系：`{メジャー}.{マイナー}.{ビルド}`（例 4.8.3345）——MC バージョンごとに並行系統を維持（1.21.1 系は 4.8.x）。コンテンツ追加＝マイナー以上、修正＝ビルド
- リリース刻み：MC バージョン追随は安定系ごと。章・領域の追加は完成した塊ごとにリリース（不完全な領域を出さない）
- 長期開発：初期リリース 2011 年〜継続——「完成形で出す→段階追加」より「安定系に合わせて育てる」運用

**大型 MOD の段階リリース一般形**：
- 内部テスト → 限定招待（closed）→ 公開アルファ（`alpha` チャネル・機能限定）→ ベータ → リリース
- ストーリー性のある MOD は公開情報の順序を設計する（説明文に核心ネタバレを書かない・「play blind」推奨の明記・スクリーンショットは序盤のみ）

**配信者への到達**（docs/46 §5.4・§9 出典）：
- ぶいきゃす型サーバーイベント（2025-12 実績：VTuber35名×MOD 入りマルチサーバー×レンタルサーバー提供）が日本の MC MOD 配信者到達の確立形式——**個別配布よりイベント運用が主経路**（D-7 承認済み）
- サーバーイベント運営が必要とするもの：導入の一発化（パックまたはワンクリック）・サーバーデフォルト値の適正・配信素材（紹介文・サムネ・ガイド）

### 1.3 ライセンスの選択肢（D-6 の比較材料）

| 候補 | modpack 同梱 | 再配布 | 二次創作 | 備考 |
|---|---|---|---|---|
| MIT | 無条件可 | 可 | 可 | 最もパック親和・MOD 界で広く使用 |
| LGPL-3.0 | 可 | 可（条件付） | 可 | 修正の開示義務あり・大型 MOD で実績 |
| ARR＋パック許諾条項 | 条項で明示許可 | 不可（条項次第） | 制限可 | 管理は細かいが条項の自作管理が必要 |
| ARR（無条件） | 不可 | 不可 | 不可 | **modpack 収録条件 D-4 と矛盾——不適格** |

- Modrinth は SPDX 識別子が必須——ARR の場合は `LicenseRef-` カスタム表記の扱いを要確認
- 素材権利台帳（LICENSES-AUDIO.md）の作成は Phase 1 着手までに確定済み（42-U3-Q4 承認）

### 1.4 段階リリースと本作の構造的接点

- 本作は**章構造**（序＋5章＋終章）——章追加が自然なリリース刻みの単位（「没の国に少しずつ世界が増えていく」= テーマと一致）
- 公開アルファは**垂直スライス範囲（OP〜序〜第1章〜村〜帰還）を収録**する想定がスライス計画と整合（docs/40・41 の判定入力がアルファ可否の材料）
- ネタバレ構造（R-38）：由来物の正体・没腐・結末構造・切り抜き瞬間は告知しない（docs/41 §2.1 除外条件②の延長が公開物にも効く）

## 3. 設計原則（P-RL——判断の座標）

| ID | 原則 |
|---|---|
| P-RL-01 | **段階リリース＝章追加の刻みで世界が育つ**。アルファ→正式→章追加の刻み方自体が「没の国に少しずつ世界が増える」テーマの表現——リリース単位は章/環礁の完成塊 |
| P-RL-02 | **ネタバレ保全＝公開情報の順序設計**。説明文・トレーラー・素材は「触れる前の発見」を毀損しない粒度——核心（由来物の正体・没腐・結末構造・切り抜き瞬間）は告知対象外 |
| P-RL-03 | **導入の一発化**。サーバーイベント運用を阻害しない——パック化・ワンクリック導線・サーバーデフォルト値の適正が公開品質の一部 |
| P-RL-04 | **段間移行はゲート駆動**。公開アルファ可否・正式化・章追加公開は暢感でなく docs/41 の判定入力＋明示条件で判定 |
| P-RL-05 | 運用選択は複数案比較＋推奨案つき要承認。正典変更は直接書かず要承認へ |
| P-RL-06 | 外在化——決定・判定・イベントは票/表に残す（STATE.md・Issue コメントと連動） |
| P-RL-07 | 正典値は引用のみ——値の正本は各ソース書（D-1〜D-7・41-U系・42-U系の承認値） |
| P-RL-08 | **単独開発の運用実在性**——公開運用（モデレーション・変更履歴・多言語対応・サポート導線）が個人開発で回る規模に収める |
| P-RL-09 | 波及設計——配信者到達（D-7）は「プレイ動画を見た人が自分も捨てたくなる」波及を目標に素材と導線を設計する |

## 6. 未決想定枠（要承認として出ると予想される論点）
