## 0. 位置づけ・運用ルール

### 0.1 本書の役割——全リスクの唯一の正本

本書は The Understory の**全リスクを集約する唯一の台帳（正本）**である（G-RR-02）。以後に生じるリスク・前提・依存・課題はすべて本書の行として管理し、個別書が各行の正本を持つ運用はしない。Issue #7 熟考コメントのとおり「台帳がないと、リスクは設計時に一度検討されて沈む状態で死ぬ」——本書はその沈降を防ぐ装置であり、「どのリスクが今赤いか・どの緩和策が発火済みか」を一括で見る場所である。

- **引き継ぎ**：docs/00 §5 の主要リスク5行・docs/40 §9 のスライス固有リスク行・docs/41 §8.4 のリードタイム設計は本書 §2 の行として引き継ぐ。引き継ぎは行の形への整流であって語彙・値の改変ではない——既存行の語彙・リードタイム値（L2 募集＝実施予定の約4週前から開始可・配信者交渉＝最長の不確定要素で L2 実施と並行開始）はそのまま用いる（G-RR-02/04・docs/59 制作上の注意「既存行の尊重」）
- **参照置換**：引き継ぎ元の各書の台帳行は「docs/42 参照」への置換を提案する（各正典への直接改変は要承認——42-U1-Q5・G-RR-02）。置換後も値の正本は各正典に残り、本書は「行を持ち・接続先を指す」形をとる（§0.4）
- **新規行の流入**：各 Issue の手渡し行（例：docs/40 §9「Issue #7」行・docs/41 §10.2）・レビューで検出した兆候はすべて本書へ行追加する。追加手順は §3 が定める

### 0.2 対象範囲

扱う範囲はプロジェクト全期（Phase 0 設計〜公開後まで）の以下の全種別である（docs/59 §1.2/§5・Issue #7 熟考コメント）：

- **現行の密集領域**は垂直スライス工程（docs/40・docs/41・Issue #5/#6/#13）だが、量産構造・配布・公開後運用まで射程に置く

本書が**扱わないもの**：リスクの緩和・対処の実施そのもの（Phase 0 制約——§0.5）、および個別書が正として持つ設計値の定義（§0.4 引用のみ原則）。

### 0.3 RAID 並記と用語定義

本書は RAID 構造を採用し、リスクだけでなく「前提」「依存」「課題」も同一の監視対象として並記する（P-RR-04・docs/59 §1.2）。前提が崩れることはリスクの発生そのものであり、依存先の変化はリスク源である——分けて管理すると兆候の検出が遅れるため、同一の行フォーマット・スコア規則・ライフサイクルで管理する。

| 行種別 | 定義 | 台帳上の扱い |
|---|---|---|
| **リスク** | 未発生の負の事象——「〈条件〉が起きたら〈被害〉」の形で記述する（§0.7） | 全ライフサイクルを適用（§1.6） |
| **前提** | 設計・工程が成り立つための条件（例：個別層ハイブリッドの確定・JEI 必須依存・modpack 収録条件5点）。崩れた場合にリスク化する | 記述は「前提 X が崩れたら〈被害〉」の形。発生確率＝前提が崩れる見込み。恒久確定した前提は退場（§1.10） |
| **依存** | 外部の要素・主体への依存（NeoForge 1.21.1/Java 21・JEI/Patchouli/GeckoLib・配信者網・募集母集団・Modrinth/CurseForge） | 依存先の変更・停止・枯渇・ポリシー改定を早期警戒指標として監視する行。緩和は代替経路・バージョン固定方針の明文化・同梱形態等 |
| **課題** | 既に発生した問題・未解消の残件（Issue #35 未着手・保守方針未決・判定保留項目等） | 発生確率＝「既発生」、初期状態＝realized。緩和ではなく対処計画を持ち、解消した時点で closed（§1.6・§1.10） |

### 0.7 記述規則

行・節の記述は以下に従う（P-RR-01/03/05・G-RR-09・docs/59 §1.1〜1.3）：

- **if/then 構文**：リスク記述は「〈条件〉が起きたら〈被害〉」で書き、**なぜ負なのか**（主題装置・配信映え・体験品質・工数への接続）を記述内で言明する。一般論的な不安（「開発が遅れるかも」）は行にしない
- **機械的判定可能性**：兆候・発火判定・緩和の記述は、第三者（将来の自分・後続エージェント）が読んでそのまま判定・実行できる粒度にする。「様子を見る」「注意する」で終わる行を作らない。記憶に残す運用は禁止（P-RR-05——本リポジトリ自体が属人化の緩和であり、台帳はその一員）
- **発火→行動の結線**：全行に早期警戒指標と発火時の緩和/対処を持たせる（§1.7）。発火したら「誰が・何を・どこへ記録して実行するか」まで書く——「発生してから考える」行を作らない（P-RR-03）
- **採番**：行 ID＝行種別に関わらず `R-XX` 連番（欠番は詰めず、退場行の番号を再利用しない——判断履歴の連続性・§1.10）。要承認 ID＝`42-U{n}-Q{m}` 完全修飾で §4 に集約（G-RR-09）。統合後の運用中新規起票は §4.1 のとおり `42-Q{n}` 正ID系（採番方式は 42-U4-Q9 承認済み・2026-10-05）
- **日本語**：本文・表・要承認は日本語（コード識別子・状態語彙は英語可）

## 1. 評価規則

### 1.1 評価の型——スコア規則を先に固定

本書の全行は**深刻度（S）×発生確率（P）のスコア**で評価する（docs/59 §1.2・P-RR-02）。スコア規則は行の評価に先立って本節で固定し、行の追加・再評価はこの規則で機械的に行う——見てから規則を動かさない。

- **現在スコア**＝深刻度 S（1〜5）×発生確率 P（1〜3）の積（範囲 1〜15——§1.4）
- **残存リスク**：緩和策が発動した後に許容したい着地点。行の残存リスク列に「緩和後の想定スコア（目標リスク相当）」を併記する（docs/59 §1.1「現在リスク vs 目標リスク」——現状と着地点の両方を持つ）
- 再評価時は現在スコアと判定日を更新する。再評価履歴の保持・記録形は §3 の監視運用に委譲する
- スコア構成の段数・合成方式は運用選択として **42-U1-Q1** へ起票し、承認済み（2026-10-05——本節どおり確定）

### 1.2 深刻度の定義——工数被害＋面白さ被害の二軸

深刻度は **2 軸の大きい方**を採る（P-RR-07——本作の価値は面白さであり、工数被害が小さくても主題装置を損なう行は上位に置く。逆に体験への被害が小さくても工期を大きく毀損する行は上位に置く）。記入は「S{n}（工数 S{a}・面白さ S{b}）」の形で両軸を併記し、どちらの軸が深刻度を駆動したかを残す（エスカレーション判定＝§1.9 に使う）。

**軸A：工数被害**（工数の増加・遅延の規模。段差は正典の工期単位——スパイク数日〜2週・リードタイム週単位（docs/41 §8.4・docs/57 §6 工数目安）——に揃える）：

| 段 | 名称 | 定義 |
|---|---|---|
| S5 | 致命 | プロジェクトの継続・公開自体が成り立たない（EULA 抵触・法務停止を含む）、または量産計画・Phase 構造の全再設計（数か月級の巻き戻し） |
| S4 | 甚大 | スライス構造・先行ゲート5点（40-Q8）・Phase 計画の変更を伴う（数週〜1か月級の再設計） |
| S3 | 大 | 工程単位の一部遅延・設計代替の発動（数日〜2週級——スパイク1本分を失う程度） |
| S2 | 中 | 限定範囲の修正・再作業（数日以内） |
| S1 | 小 | 点検・微修正で吸収できる揺れ（〜1日） |

**軸B：面白さ被害**（主題装置・配信映え・体験品質への被害）：

| 段 | 名称 | 定義 |
|---|---|---|
| S5 | 致命 | 主題装置の喪失——没の掴み・拾得・語り・綴じ・選択の記憶が成立せず MOD として成立しない（P-VS-02・G-VS-07 識別子：あなたが捨てたもの・拾得図鑑・ノミ・結末綴じ） |
| S4 | 甚大 | 完成品質ライン（40-Q7①〜⑨）を満たせない体験の致命傷——docs/41 §7.5.2 致命傷認定線4条相当／配信映えの根幹（切り抜き構造・章＝配信回・30秒ルール——docs/17）の喪失 |
| S3 | 大 | 体験品質の一部劣化——巻き戻し①〜③層（表現・数値・仕組み——docs/40 §5.4）で回収可能な失敗・配信価値の限定損失（一部の見せ場の沈黙） |
| S2 | 中 | 限定場面・二次装置の品質低下（一次導線は成立） |
| S1 | 小 | 体感にほぼ影響しない揺れ |

### 1.3 発生確率の定義

| 段 | 名称 | 定義 |
|---|---|---|
| P3 | 高 | 次のレビュー境界までに発生する見込みが高い／早期警戒指標の兆候が既に観測されている／対象の不確定要素が未解消のまま工程が進行している（目安 60%超） |
| P2 | 中 | 工程内で発生しうる・条件次第（目安 30〜60%） |
| P1 | 低 | 現状では起きそうにない（目安 30%未満） |

- **制御不能リスク**（他社類似作の先行・外部ポリシー変更等）は確率を下げられない——低く見積もらず実態の確率で置き、被害側を発生時対処・緩和で補う（docs/59 §1.1）
- **兆候発火＝確率の再評価信号**：早期警戒指標が発火した行は発生確率を P3 相当として再評価し、状態を mitigating へ遷移する（§1.6）
- 課題行は「既発生」のため発生確率欄は「—」とする（§1.6）

### 1.4 現在スコアと帯

現在スコア＝S×P（1〜15）。帯は監視・エスカレーションの優先度である：

| 帯 | スコア | 扱い |
|---|---|---|
| 赤 | 10〜15 | 最優先監視。エスカレーション対象（§1.9）。週次点検で必ず早期警戒指標を確認する |
| 黄 | 5〜9 | 通常監視。週次点検で確認する |
| 緑 | 1〜4 | 低優先監視。退場候補でもある（§1.10） |

**例外**：深刻度 S5 の行は確率に依らずエスカレーション対象（§1.9——S5×P1＝5 は帯としては黄だが扱いは赤に準ずる）。課題行は確率を持たないため帯を持たない（対処管理は状態で行う——§1.6）。

|---|---|---|
| 技術 | 実装方式・性能・同期等の技術的成立性 | Issue #13 PoC ゲート・個別層同期・世界生成（H-03/05） |

分類列は「〈カテゴリ〉・〈行種別〉」の形で併記する（例：「外部依存・依存」「技術・リスク」「法務・IP・課題」）。行種別は §0.3・§1.6 の4種（リスク/前提/依存/課題）。

### 1.6 行種別（RAID）と状態ライフサイクル

全行は以下の5状態で管理する（docs/59 §1.3）：

| 状態 | 定義 | 遷移条件 |
|---|---|---|
| identified | 起票済み・評価未完成または監視未開始 | 必須フィールド記入＋スコア付け完了で watching へ |
| watching | 早期警戒指標を監視中・トリガー未発火 | トリガー発火 or 予防緩和の開始で mitigating へ／発生確認で realized へ |
| mitigating | 緩和策を実施中（実施主体＝ユーザー・該当 Issue——G-RR-01） | 緩和完了し残存スコアへ再評価したら watching へ／それでも発生したら realized へ |
| realized | リスクが発生し課題として対処中（対処記録を行へ連結する） | 対処完了で closed へ |
| closed | 解消条件を満たし退場（理由・判定日必須——§1.10） | 再発条件充足で identified へ戻す（新規行にしない） |

種別ごとの適用：

- **リスク行**：上記ライフサイクルをそのまま適用
- **前提行・依存行**：同じライフサイクルを適用。前提の崩壊・依存の断絶が確認されたら realized へ（対象課題へ派生するか新規リスク行を起票し、接続先に記す）。恒久確定した前提・確立済みの依存管理は closed へ
- **課題行**：初期状態＝realized（既発生のため）。発生確率「—」・現在スコア欄は深刻度のみ（記入例「S4／既発生」）。緩和設計列ではなく「発生時対処」列に対処計画を持つ
- 種別別の採点・運用適用は運用選択として **42-U1-Q4** へ起票し、承認済み（2026-10-05——本節どおり確定）

### 1.9 エスカレーション規則

**即時エスカレーション**（検出次第・次回レビューを待たない）——以下のいずれかに該当する行は、推奨案つきでユーザー承認へ上げる（G-RR-08・docs/59 §1.3）。**適用範囲**：本規則は台帳の運用中の検出——行追加・スコア上昇・トリガー発火・Issue 受入等の状況変化——に適用する。§2 発行時の初回記帳で深刻度 S5 と評価された行は、§3.0 の発行票への全件列挙＝ユーザーへの一括提示をもってエスカレーション済みとする（行は watching で起票——エスカレーション起票自体は状態を動かさず、行の遷移は §1.6/§3.5 の条件どおり・トリガー発火または予防緩和の開始で別途発生する）：

- (a) 深刻度 S5 の行（確率不問——主題装置喪失・プロジェクト継続不能級）
- (b) 現在スコアが赤帯（≥10）へ入った行
- (c) **EULA 赤信号**——収益系の検討発生自体を対象とする行（G-RR-07：本プロジェクトは無償公開前提であり、収益化検討の発生は即エスカレーション事由）
- (d) 緩和・対処が「面白さの根幹・正典値・方向性」の変更を伴う行（巻き戻し④⑤層相当——docs/40 §5.4。⑤正典層はユーザー決裁のみ）

**定期エスカレーション**（レビュー時に判定）：発生確率が直近2回のレビューで連続上昇した行、または黄→赤へ遷移した行をユーザーへ共有する。

**形式**：`42-U{n}-Q{m}` の要承認として §4 へ起票し、推奨案と書き戻し先を明記する（G-RR-09）。エスカレーション未裁のまま、深刻度上位の対処・正典値に触れる変更を独断で実施しない（G-RR-01/08）。閾値は運用選択として **42-U1-Q2** へ起票し、承認済み（2026-10-05——本節どおり確定）。

### 1.10 退場規則

行は増やすだけでなく、解消条件と退場記録を持つ（P-RR-06）。**退場＝削除ではない**——closed 行は判断履歴として残す（死んだリスクの記録はその根拠とともに価値を持つ）。

**解消条件**（いずれかを週次・契機レビューで判定——§3）：

- (a) **リスク源の除去**——緩和が恒久的に効き、残存リスクが許容内（緑帯相当）に収まった
- (b) **前提の恒久確定**——前提行が調査・PoC・承認により事実化した（例：Issue #13 の PoC 合格で技術前提が確定）
- (c) **課題の解消**——課題行の対処が完了した
- (d) **確定的移管**——行の管理が別 Issue・別書の正本として確立し、本書の監視対象でなくなった（「行を持ち接続先を指す」設計の行は原則継続——§0.4）
- (e) **発生→対処完了**——実害が残らず対処記録が接続先に残った

**退場記録**：closed 行は物理削除せず、「状態＝closed・退場理由・退場判定日」を行に残す。行 ID は欠番として維持し再利用しない（§0.7）。

**復活**：closed 行の再発条件が満たされた場合、新規行を作らず同じ行を identified に戻す（履歴の連続性——P-RR-05/06）。

## 3. 監視運用

> §1.8 が固定したレビュー契機（週次自己点検・Issue 完了時・Phase 境界）を、「誰が・いつ・何を・どこへ記録して実行するか」まで機械化する運用節（docs/59 §5 組版。P-RR-05 外在化＝単独開発では記憶に残す運用は禁止し、本節の手順はこの文書だけを読んだ後続の作業主体——将来の自分・別の作業セッション——がそのまま実行できる粒度で書く。P-RR-08＝レビュー義務化）。
>
> **Phase 0／Phase 1 境界**（G-RR-01）：本節が定めるのは監視・記録・判定の運用であり、緩和策・対処の実施そのものではない。早期警戒指標が発火した場合でも、本書が担うのは「発火の検出・行の状態遷移・緩和の接続先への起票」まで。実施判断はユーザーおよび該当 Issue 側に属する。

### 3.0 役割分担と記録先——「誰が・どこへ」の固定

**役割分担**（§1.8 既定・docs/41 §7.1 判定権限表の権威分離に準拠）：

| 役割 | 誰 | 何を |
|---|---|---|
| **点検実施者** | 発火時点の作業主体（制作者または作業中のエージェントセッション） | レビュー手順の実行・指標照合・行の更新・票の起票 |
| **記録者** | 同上（点検実施者が兼務） | 監視記録への追記・Issue #7 コメント・STATE.md への転記 |
| **緩和・対処の実施者** | ユーザー・接続先 Issue の担当 | 発火した緩和策の実施判断と実行（本書の管轄外——G-RR-01） |
| **承認者** | ユーザー | §4 要承認の決裁・Phase 移行判断・致命的リスクへの対処方針（G-RR-08・AGENTS.md 意思決定分業） |

同一日に複数主体が並走しても、実施済み証跡＝監視記録の直近票の日付を機械参照するため二重実施は起きない。

**記録先の固定**（どこへ書くか——一カ所に集約する分散禁止原則は §0／G-RR-02）：

| 記録対象 | 記録先 | 更新形 |
|---|---|---|
| 行の現在状態・現在スコア | 本書 §2 の行本体 | 上書き更新（判定日を併記。履歴は行に残さない） |
| レビュー票・遷移履歴・スコア履歴 | 本書 §3.8 の監視記録表 | 追記のみ（票は削除しない） |
| 要承認 | 本書 §4 の集約表 | §4.1 の採番規則で追記 |
| 外部への通知・共有 | Issue #7 コメント・接続先 Issue コメント・STATE.md | 摘要のみ（詳細は本書を参照させる） |

**起票初期状態**（発行時のブートストラップ）：§2 統合完了時点で必須フィールドが揃った行は原則 `watching` で起票する（§1.6 の遷移条件を統合時点で充足済みとみなす）。**初回記帳で深刻度 S5 と評価された行は、発行票（§3.8・RV-発行日-01）に全件列挙してユーザーへ一括提示する**——§1.9(a) の初回適用として扱い、行は `watching` で起票する（行の遷移は §1.6/§3.5 の条件どおり——トリガー発火・予防緩和の開始で別途発生する。初回記帳は「状況変化の検出」ではないため §1.9 の即時エスカレーションを逐件発動させない）。**ただし種別＝課題の行は `realized` で起票する**（§1.6——既発生のため発生確率「—」・現在スコア欄は深刻度のみ。例：R-24（Issue #35 未着手）・R-26・R-41 の課題行）。発行票（§3.8 の書式・RV-発行日-01）に全行の初期スコアを記録し、「発生確率の直近2回連続上昇」判定（§1.9）の第0期とする。

**「追加しない」判断の記録**（G-RR-06）：行追加審査で「監視対象にしない」「緩和を追加しない」と決めた場合、その判断は緩和履歴として残す——判断内容・根拠・再検討条件を、該当行の関連行または監視記録の票に記録する（正典パターン：docs/40 §7 台帳の「条件付き除外」行）。「追加しない」記録があれば、同一候補の再提案をその都度同じ結論で即座に棄却できる。

### 3.5 再評価・状態遷移の手順

**遷移駆動表**（検出→判定→遷移→記録を機械化。判定規則の正本は §1.3/§1.6）：

| 検出（どの手順で） | 判定 | 遷移 | 記録・接続 |
|---|---|---|---|
| 早期警戒指標の発火（§3.1〜3.3） | 発生確率を P3 相当に再評価（§1.3） | `watching`→`mitigating` | 行に遷移日併記・緩和列の接続先へ起票（実施判断はユーザー・Issue 側） |
| 緩和策の完了報告（Issue 受入・コメント） | 残存スコア再評価（§1.3） | `mitigating`→`watching`（残存が黄帯以下に戻る場合） | 行のスコア上書き・票に前後スコア |
| リスクの発生確認（緩和未奏功・前提崩壊の確定） | 影響の実在確認 | `watching`/`mitigating`→`realized` | 対処計画の発動接続（対象 Issue・課題行への起票）＋要承認なら §4 |
| 対処完了・前提の恒久確定（出典 Issue の承認・着地） | §1.10 の解消条件 (a)〜(e) 充足 | `realized`/`watching`/`mitigating`→`closed` | §3.6 の退場記録 |
| 再発条件の充足（closed 行の条件が再び成立） | 再発確認 | `closed`→`identified`（行復活——新規行にはしない） | 復活理由を票に記録（判断履歴の連続性） |
| 発火なし・確率低下のみ | 確率再評価（§1.3） | 状態維持・スコアのみ更新 | 行のスコア上書き・票に記録 |

**記入形**：行の状態列は「状態（判定日 YYYY-MM-DD）」、スコア列は現在値を上書きする。遷移の履歴・理由は監視記録の票が正本——行本体には最新状態のみを持たせ、票による時系列で遡れるようにする（行への履歴内包は肥大化させるため行わない）。

### 3.6 退場記録の扱い

P-RR-06（終了条件の設計）と §1.10 の運用面：

- **closed は削除ではない**。行は §2 内に残し、週次走査（§3.1 P5）では退場候補としてのみ確認する。移動・削除しない——判断履歴の完全性を保つ（docs/40 §7 台帳が「切ったもの」を台帳に残すのと同型）。
- **記入形**：状態列を「closed（判定日）」とし、退場理由＝§1.10 の解消条件 (a)〜(e) のどれに該当するか＋根拠一文を行に残す（例：「(a) リスク源の除去——対象機能を docs/40 §7 台帳で条件付き除外として着地したため行のリスク源が消えた」）。
- **前提行の closed** は「出典 Issue の承認・着地で恒久確定」のみ——Phase を跨ぐ前提は §3.3 P3 で一括検証してから判定する。
- **復活**：再発条件が成立した行は `identified` へ戻す（§3.5）。新規行にしない——同一リスクの履歴を一行で追えることが監視の要件。
- **退場一覧**：Phase 境界レビュー（§3.3 P5）で closed 行を集計し、退場履歴を棚卸し票に残す。

### 3.7 エスカレーションの運用

§1.9 の基準（変更しない——列挙は §1.9 本文どおり・引用のみ）を運用に落とす機械化：

- **即時系**——§1.9 の即時条件 (a)〜(d) のいずれかに該当する行を検出した場合：**(a) 深刻度 S5 の行（確率不問——黄帯・緑帯に置かれる S5×P1 等も全件対象）／(b) 現在スコアが赤帯（≥10）へ入った行／(c) EULA 赤信号（収益系の検討発生自体を対象とする行——G-RR-07 の運用化本体。「収益化検討の発生」という事実の検出のみで即時起票事由になり、内容の善し悪しは本書側で評価しない）／(d) 緩和・対処が「面白さの根幹・正典値・方向性」の変更を伴う行（巻き戻し④⑤層相当——⑤正典層はユーザー決裁のみ）**。検出したレビュー内で §4 へ `42-Q{n}` 起票（運用中の新規採番規則は §4.1・42-U4-Q9 承認済み）→ **行の状態は据置**（エスカレーション起票自体は状態を動かさない——行の遷移は §1.6/§3.5 の条件どおり・トリガー発火または予防緩和の開始で別途発生する）→ 即時票を監視記録へ → Issue #7 コメントまたは完了報告でユーザーへ提示。**未裁のまま実施判断・スコア操作を先行しない**（G-RR-01/08——緩和の実施は本書の外）。
- **定期系**——§1.9 の定期条件どおり：「発生確率が直近2回のレビューで連続上昇した行」「黄→赤へ遷移した行」を週次点検 P7 で監視記録のスコア・確率履歴から機械判定し（分母＝当該行を判定対象に含んだ直近2票——§3.8）、該当行をユーザー共有の摘要に含める。
- **付帯検出**——§1.9 の条件ではないが点検中に検出し得る事項は、§4 起票事由ではなく各規定の処理へ回す：**前提崩壊の確定**→ §1.6 の遷移条件どおり §3.5 で `realized` へ遷移処理（遷移後の対処が方向性・正典値の変更を伴う場合のみ (d) で §4 起票）。**カテゴリ0件**→ その場で §1.5 の網羅確認を実施し、見落としなら §3.4 で行化・設計上の空白なら票に記録のみ（起票事由ではない——§1.5 のレビュー確認項）。**面白さ損害軸 S4 以上の行**→ §1.9 に条件がないため起票事由にしないが、**帯不問で週次照合対象へ加える**扱いが確定済み（42-U4-Q8 承認済み 2026-10-05——§1.9 改訂なしの運用強化。§3.1 P2 の照合対象を参照）。
- **滞留監視**：未裁の要承認が週次点検2回分を超えて滞留した場合、滞留一覧を定期共有へ回す（42-U4-Q7 承認済み 2026-10-05——滞留一覧を Issue #7 コメント＋STATE.md 未決事項へ再提示。暫定確定運用は原則不可・運用選択系のみ条件付き許可——R-31 行の規範と整合）。

## 4. 未決・要承認集約

### 4.1 書式と採番

- **ID**：`42-U{n}-Q{m}` 完全修飾（n＝起票ユニット、m＝ユニット内連番）。ユニット割当：U1＝§0〜§1、U2＝§2 前半、U3＝§2 後半、U4＝§3〜§5。**統合後の運用中新規起票は `42-Q{n}` の連番**で追記する（docs/40 §8 が起票時 `40-U{n}-Q{m}` を統合時に `40-Q{n}` 正IDへ一元化した先例——本書は統合後もユニット接頭辞を残すが、運用追加分は正ID系に統一して起票主体の消滅後も採番が破綻しないようにする。なおこの採番方式は G-RR-09 テンプレの `42-U{n}-Q{m}` 形式からの逸脱を含むため、§4.4 の **42-U4-Q9 で明示的な承認対象**とする）。
- **列構成**：`| ID | 論点 | 選択肢の比較 | 推奨案 | 書き戻し先 | 統合元 | 状態 |`。選択肢の比較は丸投げしない「比較材料＋推奨」の形（AGENTS.md 意思決定分業）。統合元は起票ユニット・検出節・併合した旧IDを記す。
- **併合**：同一論点の重複起票は1行に併合し、併合されたIDは統合元列に記録する（欠番にしない——docs/41 §9 の併合先例）。
- **欠番**：起票後に不要となった行は削除せず状態列を「取り下げ」として残す（ID 再利用禁止）。

### 4.2 起票基準——何が要承認になるか

要承認に上げるもの（G-RR-08・AGENTS.md）：

1. 面白さの根幹・方向性に関わる決定（最終決定権はユーザー）
2. 正典値・承認値・正典節への変更を伴うもの（G-RR-05 の逆側——値の発生源への変更）
3. 複数案があり得る運用判断（本節 §3 の発火条件・記録先・権限など——複数案比較＋推奨案つきで構造化）
4. §1.9 のエスカレーション条件に該当した行の対処方針
5. Phase 0 制約を超える実施判断（docs の外への影響・実装作業の要否）

要承認に上げないもの：行・監視記録・票の追加更新、機械手順の実行（§3.9 改訂権限の運用側）。

### 4.3 集約手順（統合時・運用時）

- **統合時**：各ユニットの起票出力（`.devin-work/issue7/u{n}_open_questions.md`）を原票として本表へ転記し、統合元列に当該ユニットを記す。U2・U3 分は統合工程で追記。重複は §4.1 の併合規則で処理。
- **運用時**：§3.4 P6／§3.7 で発生した新規起票は `42-Q{n}` で本表へ追記し（採番方式は 42-U4-Q9 承認済み）、統合元列に検出経緯（票 ID・出典節）を記す。
- **承認後**：承認済み行は推奨案どおり書き戻し先へ反映し、状態列を「承認済み（日付）」へ昇格。一括承認（「承認」の一言で全件推奨案どおり採用）を可能にするため、各行は独立に成立させる（docs/40 §8／docs/41 §9 の慣行）。不採用・条件付きの場合は ID 指定で状態更新し、派生リスクは §3.4 で行化する。
