## 3. 監視運用

> §1.8 が固定したレビュー契機（週次自己点検・Issue 完了時・Phase 境界）を、「誰が・いつ・何を・どこへ記録して実行するか」まで機械化する運用節（docs/59 §5 組版。P-RR-05 外在化＝単独開発では記憶に残す運用は禁止し、本節の手順はこの文書だけを読んだ後続の作業主体——将来の自分・別の作業セッション——がそのまま実行できる粒度で書く。P-RR-08＝レビュー義務化）。
>
> **Phase 0／Phase 1 境界**（G-RR-01）：本節が定めるのは監視・記録・判定の運用であり、緩和策・対処の実施そのものではない。早期警戒指標が発火した場合でも、本書が担うのは「発火の検出・行の状態遷移・緩和の接続先への起票」まで。実施判断はユーザーおよび該当 Issue 側に属する。

### 3.0 役割分担と記録先——「誰が・どこへ」の固定

**役割分担**（§1.8 既定・docs/41 §7.1 判定権限表の権威分離に準拠）：

| 役割 | 誰 | 何を |
|---|---|---|
| **点検実施者** | 発火時点の作業主体（制作者または作業中のエージェントセッション） | レビュー手順の実行・指標照合・行の更新・票の起票 |
| **記録者** | 同上（点検実施者が兼務） | 監視記録への追記・Issue #7 コメント・STATE.md への転記 |
| **緩和・対処の実施者** | ユーザー・接続先 Issue の担当 | 発火した緩和策の実施判断と実行（本書の管轄外——G-RR-01） |
| **承認者** | ユーザー | §4 要承認の決裁・Phase 移行判断・致命的リスクへの対処方針（G-RR-08・AGENTS.md 意思決定分業） |

同一日に複数主体が並走しても、実施済み証跡＝監視記録の直近票の日付を機械参照するため二重実施は起きない。

**記録先の固定**（どこへ書くか——一カ所に集約する分散禁止原則は §0／G-RR-02）：

| 記録対象 | 記録先 | 更新形 |
|---|---|---|
| 行の現在状態・現在スコア | 本書 §2 の行本体 | 上書き更新（判定日を併記。履歴は行に残さない） |
| レビュー票・遷移履歴・スコア履歴 | 本書 §3.8 の監視記録表 | 追記のみ（票は削除しない） |
| 要承認 | 本書 §4 の集約表 | §4.1 の採番規則で追記 |
| 外部への通知・共有 | Issue #7 コメント・接続先 Issue コメント・STATE.md | 摘要のみ（詳細は本書を参照させる） |

**起票初期状態**（発行時のブートストラップ）：§2 統合完了時点で必須フィールドが揃った行は全て `watching` で起票する（§1.6 の遷移条件を統合時点で充足済みとみなす）。発行票（§3.8 の書式・RV-発行日-01）に全行の初期スコアを記録し、「直近2回連続スコア上昇」判定（§1.9）の第0期とする。

### 3.1 週次自己点検の運用

**発火条件**：監視記録の直近の週次点検票の日付から **7日を超えた最初の作業セッション** で実施する。作業が途切れた場合は再開最初のセッションがそのまま点検セッションになる。判定は票の日付を見るだけの機械判定（カレンダー固定ではなく作業駆動——根拠と代替案は §4 42-U4-Q2）。

**手順**（この順に機械実行する）：

| 手順 | 操作 | 出力 |
|---|---|---|
| P1 | 監視記録から直近2票を開き、対象行の前回・前々回スコアを確認できる状態にする | 比較基準 |
| P2 | §2 を帯で走査し、赤帯・黄帯の全行の早期警戒指標列を抽出する（緑帯は P5 の退場候補判定のみ） | 照合対象リスト |
| P3 | 各行の指標を「発火条件が満たされているか」だけで判定する。値の再定義・再導出はしない（G-RR-05——指標値の正本は各ソース書） | 発火行リスト |
| P4 | 発火行を §3.5 の遷移駆動表で処理する | 状態遷移＋緩和接続先への起票 |
| P5 | closed 候補（解消条件の充足行・恒久確定した前提行）を §3.6 の退場手順へ | 退場判定 |
| P6 | 新規行候補（点検中に検出した未起票のリスク・前提・依存・課題）を §3.4 の追加手順へ | 行追加 |
| P7 | §1.9 のエスカレーション条件（赤帯行・面白さ損害軸 S4 以上・直近2回連続上昇・黄→赤・前提崩壊・カテゴリ0件）を照合し、該当があれば §3.7 へ | §4 起票・共有 |
| P8 | 週次点検票を監視記録へ追記し、摘要を Issue #7 コメントへ残す（影響があれば STATE.md「未決事項」へも一行） | 票 RV-日付-連番 |

**所要目安**：赤・黄帯の行数 × 指標照合1回。緑帯は判定を省略するため、行数が増えても負荷は上位帯に比例する（運用実在性——G-RR-01 の「Phase 0 で作れる範囲」内の軽い手順）。

**運用例**（H-06 外部テストの人手確保行の発火処理）：週次点検で H-06 行の早期警戒指標を照合し、「募集開始から2週で応募0件」の条件が満たされていれば発火と判定（指標の例は docs/59 §1.3、募集動線・フォームは docs/41 §2.3／§8.4 の募集リードタイムが正典）。発火行は確率 P3 相当へ再評価して `watching→mitigating` に遷移させ、緩和列の接続先＝docs/41 側のフォールバック（41-U1-Q13 承認済み「Issue #17 未整備なら第1軌道（社内・知人経由）で単独実施」）の発動起票を Issue #6／#17 側へコメントで繋ぐ。行本体には「mitigating（判定日）」と現在スコアを記入し、票に遷移前後スコアを記録する。緩和の実施そのものは Issue #6/#17 側の判断——本書は検出と接続まで（G-RR-01）。

### 3.2 Issue 完了時レビューの運用

**発火条件**：設計 Issue が完了処理（完了報告・書き戻し・STATE.md 更新——AGENTS.md 終了前手順）に入った時点。完了処理の一部として実施する。

**実施者**：当該 Issue の完了処理を行った作業主体（責任分界の確定は §4 42-U4-Q4）。

**手順**：

| 手順 | 操作 |
|---|---|
| P1 | 完了する書・Issue の「手渡し」一覧を走査し、「Issue #7」「リスク台帳」「docs/42」宛の行を機械検出する（先例：docs/40 §9 の Issue #7 行＝リスク5行、docs/41 §10.2 の Issue #7 行＝実績リードタイム・新規リスク行） |
| P2 | 検出した各項目を §3.4 で行化する（リスク／前提／依存／課題の種別判定を含む） |
| P3 | 当該 Issue で確定・承認された値に依存する既存行を再評価する（前提行の恒久確定＝closed 判定、確率変動＝スコア更新） |
| P4 | 「追加しない」と判断した項目があれば、G-RR-06 の緩和履歴として判断・根拠・再検討条件を記録する（§3.4 末尾） |
| P5 | Issue 受入票を監視記録へ追記する |

Issue #7 自身の完了以降もこの手順は有効——以後の全設計書の手渡し一覧が「Issue #7」を正本流入先として指す（§5.1 の参照置換で固定化）。

### 3.3 Phase 境界レビューの運用

**発火条件**：以下のいずれかの通過時点（適用範囲の確定は §4 42-U4-Q3）——

1. **開発 Phase 移行**：STATE.md 工程9「Issue が尽きたらユーザーに Phase 1（技術検証）移行を確認」の確認時点、および以後の各 Phase 移行。
2. **垂直スライス段境界**：docs/40 §6.3 のマイルストーン M0〜M5 の各段通過・巻き戻し時（工程の段境界は前提行の成立確認が自然に発生する点）。

**手順**：

| 手順 | 操作 | 出力 |
|---|---|---|
| P1 | 全行棚卸し——状態別・帯別・カテゴリ別の行数集計。**0件のカテゴリを検出したら §1.5 の網羅確認を実施**し、見落としか設計上の空白かを判定 | 棚卸し集計 |
| P2 | 残存リスク一覧（赤・黄帯全行＋未裁要承認）を作り、**Phase 移行判断の根拠としてユーザーへ供出**する（H-16「設計後期〜実装着手前の段階で先送りリスクの再点検」——移行確認に残存リスク表を添える形で固定） | 移行判断材料 |
| P3 | Phase を跨ぐ前提行の一括検証（先行ゲート5点＝40-Q8、ADR 群の前提行など、出典 Issue が未完了の前提の成立状況） | 前提検証結果 |
| P4 | 長期 `watching` 滞留行・§4 の未裁滞留の整理（§3.7 の滞留監視） | 滞留一覧 |
| P5 | closed 行の退場一覧を棚卸し（§3.6） | 退場履歴 |
| P6 | 境界レビュー票を監視記録へ追記し、結果を STATE.md「未決事項」・Issue #7 コメントへ摘要転記 | 票＋転記 |

### 3.4 行の追加手順（新規行の流入）

**流入経路**（検出→起票の入口を全網羅する）：

| 経路 | 発火の形 | 出典・根拠 |
|---|---|---|
| ① レビュー内の新規検出 | §3.1〜3.3 の手順 P6/P4 で候補化 | 本書 |
| ② Issue 手渡し行の受入 | §3.2 の完了時走査 | docs/40 §9・docs/41 §10.2 の先例 |
| ③ 検証失敗からの行追加 | 「検証で設計前提を揺らがす失敗が出た場合は Issue #7（リスク台帳）へ行を追加する」——正典が明記する流入口 | docs/41 §7.5.2 |
| ④ 長期観測のエスカレーション | 「劣化・再現性問題は台帳へ」「#7 の新規リスク行 or 台帳再検討へ」 | docs/41 §6.7 |
| ⑤ 要承認の承認結果 | 否決・縮小・条件付き承認で新たなリスクが発生した場合（例：docs/40 §7 の条件付き除外の発動） | §4.4 |
| ⑥ 外部事象 | 依存先ポリシー変更・類似作先行・EULA 改定など制御不能系の観測（早期警戒指標の観測源） | §1.3 制御不能性の扱い |

**手順**：

| 手順 | 操作 |
|---|---|
| P1 | 重複確認——既存行の再発・別表現でないかを §2 を走査して確認（重複なら既存行の再評価で処理） |
| P2 | 種別判定——リスク／前提／依存／課題（§1.5 カテゴリ・§0 用語定義。RAID 同一台帳＝P-RR-04） |
| P3 | 採番——§0 の連番規則で R-XX を発行（統合後は残りの未使用番号の次。欠番・再利用禁止） |
| P4 | 必須フィールド記入——§0 の記述規則の行フィールド全項目（発火トリガー・緩和策の接続先・早期警戒指標・観測源まで——P-RR-01/03） |
| P5 | 初期状態判定——必須フィールド完備なら `watching`、未整備なら `identified`（§1.6） |
| P6 | 即時票（§3.8）を監視記録へ追記——起票根拠と出典を記録。§1.9 該当なら §4 へも起票 |

**「追加しない」判断の記録**（G-RR-06）：行追加審査で「監視対象にしない」「緩和を追加しない」と決めた場合、その判断は緩和履歴として残す——判断内容・根拠・再検討条件を、該当行の関連行または監視記録の票に記録する（正典パターン：docs/40 §7 台帳の「条件付き除外」行）。「追加しない」記録があれば、同一候補の再提案をその都度同じ結論で即座に棄却できる。

### 3.5 再評価・状態遷移の手順

**遷移駆動表**（検出→判定→遷移→記録を機械化。判定規則の正本は §1.3/§1.6）：

| 検出（どの手順で） | 判定 | 遷移 | 記録・接続 |
|---|---|---|---|
| 早期警戒指標の発火（§3.1〜3.3） | 発生確率を P3 相当に再評価（§1.3） | `watching`→`mitigating` | 行に遷移日併記・緩和列の接続先へ起票（実施判断はユーザー・Issue 側） |
| 緩和策の完了報告（Issue 受入・コメント） | 残存スコア再評価（§1.3） | `mitigating`→`watching`（残存が黄帯以下に戻る場合） | 行のスコア上書き・票に前後スコア |
| リスクの発生確認（緩和未奏功・前提崩壊の確定） | 影響の実在確認 | `watching`/`mitigating`→`realized` | 対処計画の発動接続（対象 Issue・課題行への起票）＋要承認なら §4 |
| 対処完了・前提の恒久確定（出典 Issue の承認・着地） | §1.10 の解消条件 (a)〜(e) 充足 | `realized`/`watching`/`mitigating`→`closed` | §3.6 の退場記録 |
| 再発条件の充足（closed 行の条件が再び成立） | 再発確認 | `closed`→`identified`（行復活——新規行にはしない） | 復活理由を票に記録（判断履歴の連続性） |
| 発火なし・確率低下のみ | 確率再評価（§1.3） | 状態維持・スコアのみ更新 | 行のスコア上書き・票に記録 |

**記入形**：行の状態列は「状態（判定日 YYYY-MM-DD）」、スコア列は現在値を上書きする。遷移の履歴・理由は監視記録の票が正本——行本体には最新状態のみを持たせ、票による時系列で遡れるようにする（行への履歴内包は肥大化させるため行わない）。

### 3.6 退場記録の扱い

P-RR-06（終了条件の設計）と §1.10 の運用面：

- **closed は削除ではない**。行は §2 内に残し、週次走査（§3.1 P5）では退場候補としてのみ確認する。移動・削除しない——判断履歴の完全性を保つ（docs/40 §7 台帳が「切ったもの」を台帳に残すのと同型）。
- **記入形**：状態列を「closed（判定日）」とし、退場理由＝§1.10 の解消条件 (a)〜(e) のどれに該当するか＋根拠一文を行に残す（例：「(d) 対象機能の削除——docs/40 §7 台帳で条件付き除外として着地」）。
- **前提行の closed** は「出典 Issue の承認・着地で恒久確定」のみ——Phase を跨ぐ前提は §3.3 P3 で一括検証してから判定する。
- **復活**：再発条件が成立した行は `identified` へ戻す（§3.5）。新規行にしない——同一リスクの履歴を一行で追えることが監視の要件。
- **退場一覧**：Phase 境界レビュー（§3.3 P5）で closed 行を集計し、退場履歴を棚卸し票に残す。

### 3.7 エスカレーションの運用

§1.9 の基準（変更しない——引用のみ）を運用に落とす機械化：

- **即時系**（赤帯行の検出・面白さ損害軸 S4 以上・前提崩壊の確定）：検出したレビュー内で §4 へ `42-Q{n}` 起票（運用中の新規採番規則は §4.1）→ 行を `mitigating` へ遷移 → 即時票を監視記録へ → Issue #7 コメントまたは完了報告でユーザーへ提示。**未裁のまま実施判断・スコア操作を先行しない**（G-RR-01/08——緩和の実施は本書の外）。
- **定期系**（「直近2回連続スコア上昇」「黄→赤」）：週次点検 P7 で監視記録のスコア履歴から機械判定し、該当行をユーザー共有の摘要に含める。
- **滞留監視**：未裁の要承認が週次点検2回分を超えて滞留した場合、滞留一覧を定期共有へ回す（ユーザー単点決裁依存への対策——確定は §4 42-U4-Q7）。

### 3.8 監視記録（票の書式・記録先・履歴保持）

監視記録は本書内に常設する「票」の追記表——**記録の唯一の正本**（分散させない）。

**票の種別**：週次点検票／Issue 受入票／境界レビュー票／即時イベント票の4種。

**票のフィールド**（書式）：

| フィールド | 内容 |
|---|---|
| 票 ID | `RV-<YYYY-MM-DD>-<連番>`（当日複数票の区別用） |
| 種別 | 上記4種のいずれか |
| 実施者 | 作業主体の識別（制作者／セッション識別子） |
| 対象行 | R-XX（複数可・全行走査の場合は「全行」） |
| 判定サマリ | 発火有無／遷移（遷移前→遷移後＋前後スコア）／行追加／退場／エスカレーション／受入 |
| 行動結果 | 起票先（Issue コメント・§4 の ID・STATE.md 行） |
| 証跡 | リンク・コメント等の参照 |

スコア履歴は各票の「遷移後スコア」記録で保持し、§1.9「直近2回連続上昇」の分母＝直近2票を機械参照可能にする。記録先の確定（本書内表を正本とする案・Issue #7 コメント正本案等の比較）は §4 42-U4-Q1。

### 3.9 台帳自体の保守と改訂権限

- **健全性チェック**（週次点検 P5 と併せて実施）：カテゴリ0件検出・参照先節（引用元の正典節・接続先 Issue）の存在確認——正典改廃で参照が切れたら行の根拠列を更新し票に記録。
- **二重管理の是正**：個別書に分散したリスク記録を検出したら、§3.2 の受入手順で正本（本書）へ集約し、検出元には参照注記を残す（G-RR-02）。
- **改訂権限**：§0〜§1 の評価規則・本節の運用手順の変更は方向性に関わるため要承認（§4 起票——docs/41 §7.1「判定基準の事後変更禁止」と同型の権威分離）。行・監視記録・票の追加更新は運用者の機械実施で承認不要。確定は §4 42-U4-Q5。

## 4. 未決・要承認集約

> docs/42 全体で検出した要承認事項の**唯一の集約台帳**（G-RR-09・docs/41 §9／docs/40 §8 の集約慣行に準拠）。§0〜§2 で検出した起票は全て本節に集まり、運用中の新規起票も本表へ追記する。承認はユーザーが行い、承認済み行は書き戻し先へ反映して状態を昇格させる。

### 4.1 書式と採番

- **ID**：`42-U{n}-Q{m}` 完全修飾（n＝起票ユニット、m＝ユニット内連番）。ユニット割当：U1＝§0〜§1、U2＝§2 前半、U3＝§2 後半、U4＝§3〜§5。**統合後の運用中新規起票は `42-Q{n}` の連番**で追記する（docs/40 §8 が起票時 `40-U{n}-Q{m}` を統合時に `40-Q{n}` 正IDへ一元化した先例——本書は統合後もユニット接頭辞を残すが、運用追加分は正ID系に統一して起票主体の消滅後も採番が破綻しないようにする）。
- **列構成**：`| ID | 論点 | 選択肢の比較 | 推奨案 | 書き戻し先 | 統合元 | 状態 |`。選択肢の比較は丸投げしない「比較材料＋推奨」の形（AGENTS.md 意思決定分業）。統合元は起票ユニット・検出節・併合した旧IDを記す。
- **併合**：同一論点の重複起票は1行に併合し、併合されたIDは統合元列に記録する（欠番にしない——docs/41 §9 の併合先例）。
- **欠番**：起票後に不要となった行は削除せず状態列を「取り下げ」として残す（ID 再利用禁止）。

### 4.2 起票基準——何が要承認になるか

要承認に上げるもの（G-RR-08・AGENTS.md）：

1. 面白さの根幹・方向性に関わる決定（最終決定権はユーザー）
2. 正典値・承認値・正典節への変更を伴うもの（G-RR-05 の逆側——値の発生源への変更）
3. 複数案があり得る運用判断（本節 §3 の発火条件・記録先・権限など——複数案比較＋推奨案つきで構造化）
4. §1.9 のエスカレーション条件に該当した行の対処方針
5. Phase 0 制約を超える実施判断（docs の外への影響・実装作業の要否）

要承認に上げないもの：行・監視記録・票の追加更新、機械手順の実行（§3.9 改訂権限の運用側）。

### 4.3 集約手順（統合時・運用時）

- **統合時**：各ユニットの起票出力（`.devin-work/issue7/u{n}_open_questions.md`）を原票として本表へ転記し、統合元列に当該ユニットを記す。U2・U3 分は統合工程で追記。重複は §4.1 の併合規則で処理。
- **運用時**：§3.4 P6／§3.7 で発生した新規起票は `42-Q{n}` で本表へ追記し、統合元列に検出経緯（票 ID・出典節）を記す。
- **承認後**：承認済み行は推奨案どおり書き戻し先へ反映し、状態列を「承認済み（日付）」へ昇格。一括承認（「承認」の一言で全件推奨案どおり採用）を可能にするため、各行は独立に成立させる（docs/40 §8／docs/41 §9 の慣行）。不採用・条件付きの場合は ID 指定で状態更新し、派生リスクは §3.4 で行化する。
