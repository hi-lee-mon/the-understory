## 0. 位置づけ・運用ルール

### 0.1 本書の役割——全リスクの唯一の正本

本書は The Understory の**全リスクを集約する唯一の台帳（正本）**である（G-RR-02）。以後に生じるリスク・前提・依存・課題はすべて本書の行として管理し、個別書が各行の正本を持つ運用はしない。Issue #7 熟考コメントのとおり「台帳がないと、リスクは設計時に一度検討されて沈む状態で死ぬ」——本書はその沈降を防ぐ装置であり、「どのリスクが今赤いか・どの緩和策が発火済みか」を一括で見る場所である。

- **引き継ぎ**：docs/00 §5 の主要リスク5行・docs/40 §9 のスライス固有リスク行・docs/41 §8.4 のリードタイム設計は本書 §2 の行として引き継ぐ。引き継ぎは行の形への整流であって語彙・値の改変ではない——既存行の語彙・リードタイム値（L2 募集＝実施予定の約4週前から開始可・配信者交渉＝最長の不確定要素で L2 実施と並行開始）はそのまま用いる（G-RR-02/04・docs/59 制作上の注意「既存行の尊重」）
- **参照置換**：引き継ぎ元の各書の台帳行は「docs/42 参照」への置換を提案する（各正典への直接改変は要承認——42-U1-Q5・G-RR-02）。置換後も値の正本は各正典に残り、本書は「行を持ち・接続先を指す」形をとる（§0.4）
- **新規行の流入**：各 Issue の手渡し行（例：docs/40 §9「Issue #7」行・docs/41 §10.2）・レビューで検出した兆候はすべて本書へ行追加する。追加手順は §3 が定める

### 0.2 対象範囲

扱う範囲はプロジェクト全期（Phase 0 設計〜公開後まで）の以下の全種別である（docs/59 §1.2/§5・Issue #7 熟考コメント）：

- **分類系統**：技術・スコープ・工数/人手・法務/IP・外部依存・スケジュール・品質・コミュニティ（§1.5）
- **行種別**：リスク・前提・依存・課題の RAID 並記（§0.3・§1.6）
- **現行の密集領域**は垂直スライス工程（docs/40・docs/41・Issue #5/#6/#13）だが、量産構造・配布・公開後運用まで射程に置く

本書が**扱わないもの**：リスクの緩和・対処の実施そのもの（Phase 0 制約——§0.5）、および個別書が正として持つ設計値の定義（§0.4 引用のみ原則）。

### 0.3 RAID 並記と用語定義

本書は RAID 構造を採用し、リスクだけでなく「前提」「依存」「課題」も同一の監視対象として並記する（P-RR-04・docs/59 §1.2）。前提が崩れることはリスクの発生そのものであり、依存先の変化はリスク源である——分けて管理すると兆候の検出が遅れるため、同一の行フォーマット・スコア規則・ライフサイクルで管理する。

| 行種別 | 定義 | 台帳上の扱い |
|---|---|---|
| **リスク** | 未発生の負の事象——「〈条件〉が起きたら〈被害〉」の形で記述する（§0.7） | 全ライフサイクルを適用（§1.6） |
| **前提** | 設計・工程が成り立つための条件（例：個別層ハイブリッドの確定・JEI 必須依存・modpack 収録条件5点）。崩れた場合にリスク化する | 記述は「前提 X が崩れたら〈被害〉」の形。発生確率＝前提が崩れる見込み。恒久確定した前提は退場（§1.10） |
| **依存** | 外部の要素・主体への依存（NeoForge 1.21.1/Java 21・JEI/Patchouli/GeckoLib・配信者網・募集母集団・Modrinth/CurseForge） | 依存先の変更・停止・枯渇・ポリシー改定を早期警戒指標として監視する行。緩和は代替経路・バージョン固定方針の明文化・同梱形態等 |
| **課題** | 既に発生した問題・未解消の残件（Issue #35 未着手・保守方針未決・判定保留項目等） | 発生確率＝「既発生」、初期状態＝realized。緩和ではなく対処計画を持ち、解消した時点で closed（§1.6・§1.10） |

### 0.7 記述規則

行・節の記述は以下に従う（P-RR-01/03/05・G-RR-09・docs/59 §1.1〜1.3）：

- **if/then 構文**：リスク記述は「〈条件〉が起きたら〈被害〉」で書き、**なぜ負なのか**（主題装置・配信映え・体験品質・工数への接続）を記述内で言明する。一般論的な不安（「開発が遅れるかも」）は行にしない
- **機械的判定可能性**：兆候・発火判定・緩和の記述は、第三者（将来の自分・後続エージェント）が読んでそのまま判定・実行できる粒度にする。「様子を見る」「注意する」で終わる行を作らない。記憶に残す運用は禁止（P-RR-05——本リポジトリ自体が属人化の緩和であり、台帳はその一員）
- **発火→行動の結線**：全行に早期警戒指標と発火時の緩和/対処を持たせる（§1.7）。発火したら「誰が・何を・どこへ記録して実行するか」まで書く——「発生してから考える」行を作らない（P-RR-03）
- **採番**：行 ID＝行種別に関わらず `R-XX` 連番（欠番は詰めず、退場行の番号を再利用しない——判断履歴の連続性・§1.10）。要承認 ID＝`42-U{n}-Q{m}` 完全修飾で §4 に集約（G-RR-09）
- **日本語**：本文・表・要承認は日本語（コード識別子・状態語彙は英語可）

## 1. 評価規則

### 1.1 評価の型——スコア規則を先に固定

本書の全行は**深刻度（S）×発生確率（P）のスコア**で評価する（docs/59 §1.2・P-RR-02）。スコア規則は行の評価に先立って本節で固定し、行の追加・再評価はこの規則で機械的に行う——見てから規則を動かさない。

- **現在スコア**＝深刻度 S（1〜5）×発生確率 P（1〜3）の積（範囲 1〜15——§1.4）
- **残存リスク**：緩和策が発動した後に許容したい着地点。行の残存リスク列に「緩和後の想定スコア（目標リスク相当）」を併記する（docs/59 §1.1「現在リスク vs 目標リスク」——現状と着地点の両方を持つ）
- 再評価時は現在スコアと判定日を更新する。再評価履歴の保持・記録形は §3 の監視運用に委譲する
- スコア構成の段数・合成方式は運用選択として **42-U1-Q1** に起票する（推奨＝本節どおり）

### 1.2 深刻度の定義——工数被害＋面白さ被害の二軸

深刻度は **2 軸の大きい方**を採る（P-RR-07——本作の価値は面白さであり、工数被害が小さくても主題装置を損なう行は上位に置く。逆に体験への被害が小さくても工期を大きく毀損する行は上位に置く）。記入は「S{n}（工数 S{a}・面白さ S{b}）」の形で両軸を併記し、どちらの軸が深刻度を駆動したかを残す（エスカレーション判定＝§1.9 に使う）。

**軸A：工数被害**（工数の増加・遅延の規模。段差は正典の工期単位——スパイク数日〜2週・リードタイム週単位（docs/41 §8.4・docs/57 §6 工数目安）——に揃える）：

| 段 | 名称 | 定義 |
|---|---|---|
| S5 | 致命 | プロジェクトの継続・公開自体が成り立たない（EULA 抵触・法務停止を含む）、または量産計画・Phase 構造の全再設計（数か月級の巻き戻し） |
| S4 | 甚大 | スライス構造・先行ゲート5点（40-Q8）・Phase 計画の変更を伴う（数週〜1か月級の再設計） |
| S3 | 大 | 工程単位の一部遅延・設計代替の発動（数日〜2週級——スパイク1本分を失う程度） |
| S2 | 中 | 限定範囲の修正・再作業（数日以内） |
| S1 | 小 | 点検・微修正で吸収できる揺れ（〜1日） |

**軸B：面白さ被害**（主題装置・配信映え・体験品質への被害）：

| 段 | 名称 | 定義 |
|---|---|---|
| S5 | 致命 | 主題装置の喪失——没の掴み・拾得・語り・綴じ・選択の記憶が成立せず MOD として成立しない（P-VS-02・G-VS-07 識別子：あなたが捨てたもの・拾得図鑑・ノミ・結末綴じ） |
| S4 | 甚大 | 完成品質ライン（40-Q7①〜⑨）を満たせない体験の致命傷——docs/41 §7.5.2 致命傷認定線4条相当／配信映えの根幹（切り抜き構造・章＝配信回・30秒ルール——docs/17）の喪失 |
| S3 | 大 | 体験品質の一部劣化——巻き戻し①〜③層（表現・数値・仕組み——docs/40 §5.4）で回収可能な失敗・配信価値の限定損失（一部の見せ場の沈黙） |
| S2 | 中 | 限定場面・二次装置の品質低下（一次導線は成立） |
| S1 | 小 | 体感にほぼ影響しない揺れ |

### 1.3 発生確率の定義

| 段 | 名称 | 定義 |
|---|---|---|
| P3 | 高 | 次のレビュー境界までに発生する見込みが高い／早期警戒指標の兆候が既に観測されている／対象の不確定要素が未解消のまま工程が進行している（目安 60%超） |
| P2 | 中 | 工程内で発生しうる・条件次第（目安 30〜60%） |
| P1 | 低 | 現状では起きそうにない（目安 30%未満） |

- **制御不能リスク**（他社類似作の先行・外部ポリシー変更等）は確率を下げられない——低く見積もらず実態の確率で置き、被害側を発生時対処・緩和で補う（docs/59 §1.1）
- **兆候発火＝確率の再評価信号**：早期警戒指標が発火した行は発生確率を P3 相当として再評価し、状態を mitigating へ遷移する（§1.6）
- 課題行は「既発生」のため発生確率欄は「—」とする（§1.6）

### 1.4 現在スコアと帯

現在スコア＝S×P（1〜15）。帯は監視・エスカレーションの優先度である：

| 帯 | スコア | 扱い |
|---|---|---|
| 赤 | 10〜15 | 最優先監視。エスカレーション対象（§1.9）。週次点検で必ず早期警戒指標を確認する |
| 黄 | 5〜9 | 通常監視。週次点検で確認する |
| 緑 | 1〜4 | 低優先監視。退場候補でもある（§1.10） |

**例外**：深刻度 S5 の行は確率に依らずエスカレーション対象（§1.9——S5×P1＝5 は帯としては黄だが扱いは赤に準ずる）。課題行は確率を持たないため帯を持たない（対処管理は状態で行う——§1.6）。

分類列は「〈カテゴリ〉・〈行種別〉」の形で併記する（例：「外部依存・依存」「技術・リスク」「法務・IP・課題」）。行種別は §0.3・§1.6 の4種（リスク/前提/依存/課題）。

### 1.6 行種別（RAID）と状態ライフサイクル

全行は以下の5状態で管理する（docs/59 §1.3）：

| 状態 | 定義 | 遷移条件 |
|---|---|---|
| identified | 起票済み・評価未完成または監視未開始 | 必須フィールド記入＋スコア付け完了で watching へ |
| watching | 早期警戒指標を監視中・トリガー未発火 | トリガー発火 or 予防緩和の開始で mitigating へ／発生確認で realized へ |
| mitigating | 緩和策を実施中（実施主体＝ユーザー・該当 Issue——G-RR-01） | 緩和完了し残存スコアへ再評価したら watching へ／それでも発生したら realized へ |
| realized | リスクが発生し課題として対処中（対処記録を行へ連結する） | 対処完了で closed へ |
| closed | 解消条件を満たし退場（理由・判定日必須——§1.10） | 再発条件充足で identified へ戻す（新規行にしない） |

種別ごとの適用：

- **リスク行**：上記ライフサイクルをそのまま適用
- **前提行・依存行**：同じライフサイクルを適用。前提の崩壊・依存の断絶が確認されたら realized へ（対象課題へ派生するか新規リスク行を起票し、接続先に記す）。恒久確定した前提・確立済みの依存管理は closed へ
- **課題行**：初期状態＝realized（既発生のため）。発生確率「—」・現在スコア欄は深刻度のみ（記入例「S4／既発生」）。緩和設計列ではなく「発生時対処」列に対処計画を持つ
- 種別別の採点・運用適用は運用選択として **42-U1-Q4** に起票する（推奨＝本節どおり）

### 1.8 レビュー周期

レビュー契機は以下の3系統で義務化する（P-RR-08・docs/59 §1.3——単独開発では週次自己点検＋フェーズ境界レビューが現実解）。週次自己点検の既定実施者は現在の作業主体（制作者または作業中の Devin セッション）とする。「誰が・いつ・どこへ記録するか」の運用手順は §3 が定める：

| 契機 | 必ず行う判定 |
|---|---|
| **週次自己点検** | 全行（少なくとも赤・黄帯）の早期警戒指標の発火確認→発火行の状態遷移・確率再評価／新規行候補の検討／closed 候補の退場判定 |
| **Issue 完了時** | 当該 Issue の手渡し行の受入（行追加・出典記録）／関連行のスコア再評価（前提確定による closed 判定等） |
| **Phase 境界** | 全行の棚卸し——残存リスク一覧・上位行の状態を Phase 移行判断の根拠として供出（H-16・STATE.md 工程9）。移行可否の材料は本書 §2 の状態どおり |

レビューで必ず行う判定は「新規行の追加・スコア再評価・状態遷移・緩和策の発火判定」の4点である（docs/59 §1.3）。周期の確定は運用選択として **42-U1-Q3** に起票する（推奨＝本表どおり）。

### 1.9 エスカレーション規則

**即時エスカレーション**（検出次第・次回レビューを待たない）——以下のいずれかに該当する行は、推奨案つきでユーザー承認へ上げる（G-RR-08・docs/59 §1.3）：

- (a) 深刻度 S5 の行（確率不問——主題装置喪失・プロジェクト継続不能級）
- (b) 現在スコアが赤帯（≥10）へ入った行
- (c) **EULA 赤信号**——収益系の検討発生自体を対象とする行（G-RR-07：本プロジェクトは無償公開前提であり、収益化検討の発生は即エスカレーション事由）
- (d) 緩和・対処が「面白さの根幹・正典値・方向性」の変更を伴う行（巻き戻し④⑤層相当——docs/40 §5.4。⑤正典層はユーザー決裁のみ）

**定期エスカレーション**（レビュー時に判定）：発生確率が直近2回のレビューで連続上昇した行、または黄→赤へ遷移した行をユーザーへ共有する。

**形式**：`42-U{n}-Q{m}` の要承認として §4 へ起票し、推奨案と書き戻し先を明記する（G-RR-09）。エスカレーション未裁のまま、深刻度上位の対処・正典値に触れる変更を独断で実施しない（G-RR-01/08）。閾値の確定は運用選択として **42-U1-Q2** に起票する（推奨＝本節どおり）。

### 1.10 退場規則

行は増やすだけでなく、解消条件と退場記録を持つ（P-RR-06）。**退場＝削除ではない**——closed 行は判断履歴として残す（死んだリスクの記録はその根拠とともに価値を持つ）。

**解消条件**（いずれかを週次・契機レビューで判定——§3）：

- (a) **リスク源の除去**——緩和が恒久的に効き、残存リスクが許容内（緑帯相当）に収まった
- (b) **前提の恒久確定**——前提行が調査・PoC・承認により事実化した（例：Issue #13 の PoC 合格で技術前提が確定）
- (c) **課題の解消**——課題行の対処が完了した
- (d) **確定的移管**——行の管理が別 Issue・別書の正本として確立し、本書の監視対象でなくなった（「行を持ち接続先を指す」設計の行は原則継続——§0.4）
- (e) **発生→対処完了**——実害が残らず対処記録が接続先に残った

**退場記録**：closed 行は物理削除せず、「状態＝closed・退場理由・退場判定日」を行に残す。行 ID は欠番として維持し再利用しない（§0.7）。

**復活**：closed 行の再発条件が満たされた場合、新規行を作らず同じ行を identified に戻す（履歴の連続性——P-RR-05/06）。
