### 8.1 設計方針——暦日ではなく依存順で組み立てる

本節は Phase 1〜Phase 5 を跨ぐ公開工程を扱う。単独開発では暦日の見積が外乱（プラットフォーム審査・配信者交渉・量産係数の未確定——40-Q23）で毀損されるため、工程は**依存関係と前提条件の順序**として設計する（P-RL-08）。暦日計画は各段の実績値が入った時点で逐次更新する——リードタイム実績の回収経路は docs/41 §10.2 → docs/42 R-40 行（実績は本表の見積更新に使う）。

- **記法**：`A → B`＝B の着手には A の充足が前提。`A ∥ B`＝並行可。`〔G〕`＝ゲート（ユーザー判定）。全ゲートは「誰が・何を見て・どこへ記録するか」まで定める（P-RL-04/06）。
- **権威の所在**：段構成・各段の目的/収録範囲は §1、段間移行の判定規則・解禁判定の規則本文は §2、チャネル別の申請手順・版数・依存宣言・GitHub Releases 運用の細則は §3、LICENSE の選択肢と推奨は §4、イベント運用・提供素材は §5、公開物の情報粒度は §6、移植評価の手順は §7 が正本。**本節はそれらを工程順に並べた依存鎖であり、値を再定義しない**（G-RL-11）。
- **工程 ID**：`8-A`〜`8-N`——docs/41 §8.2 の検証工程「段0〜5」と区別するため、本書の工程はアルファベット採番とする。

### 8.5 Phase 0／Phase 2／Phase 5 の境界

本節の全工程は**公開の計画設計**である（G-RL-01）。交渉・実施の Phase 帰属は活動の側で分かれる——同一の「配信者交渉」という語でも、検証工程側と公開工程側で帰属が異なる：

- **検証工程側の交渉＝Phase 2（本書の実施対象外）**：L3 配信者候補への交渉・契約・配信実施は docs/41 の検証工程に属する（docs/41 §5.1.1：「実際の配信者への交渉・契約・配信実施は **Phase 2（S4 検証工程——Phase 1 実装完了後、docs/00 §3）**に属する」——引用のみ。同 §8.2 段0 でも「L3 候補の選定・交渉着手」は検証工程の一部）。本書はその実施を行わず、交渉・配信の実績を **8-E 判定入力（限定招待運用の実績）として観測・消費するのみ**である（G-RL-07 の対称——Issue #8 の範囲は実配信・公開アルファの実施であり、検証側の実施は Issue #6/docs/41 の範囲）。
- **公開工程側の実施＝Phase 5 以降**：掲載申請・**公開工程側の交渉**（イベント運営・公開後の配信者関係）・告知発信・パック公開・イベント実施は Phase 5（docs/00「リリース・広報」）以降の実施事項であり、個別の実施判断はその都度ユーザーの承認を取る（G-RL-12）。

## 9. 未決・要承認（43-U{n}-Q{m} 集約——唯一の台帳・推奨案・書き戻し先・統合元）

> docs/43 全体で検出した要承認事項の**唯一の集約台帳**（G-RL-13——docs/41 §9／docs/42 §4 の集約慣行に準拠）。§0〜§10 で検出した起票は全て本節に集まり、運用中の新規起票も本表へ追記する。承認はユーザーが行い、承認済み行は書き戻し先へ反映して状態を昇格させる。

### 9.1 書式と採番

- **ID**：`43-U{n}-Q{m}` 完全修飾（n＝起票ユニット、m＝ユニット内連番）。ユニット割当：**U1＝§0〜§2（位置づけ・公開段階・段間ゲート）／U2＝§3〜§4（配布運用・ライセンス法務）／U3＝§5〜§7（配信者到達・情報開示ポリシー・移植評価）／U4＝§8〜§10（工程・本節・手渡し）**。
- **統合後の運用中新規起票**：`43-Q{n}` の連番で追記する（42-U4-Q9〔承認済み 2026-10-05〕と同型の方式——統合後は起票ユニットが存在しないため。本書への適用は **43-U4-Q8** で要承認とする）。
- **列構成**：`| ID | 論点 | 選択肢の比較 | 推奨案 | 書き戻し先 | 統合元 | 状態 |`（docs/42 §4.1 の列構成に準拠）。選択肢の比較は丸投げしない「比較材料＋推奨」の形（AGENTS.md 意思決定分業）。統合元は起票ユニット・検出節・併合した ID を記す。
- **併合**：同一論点の重複起票は1行に併合し、併合された ID は統合元列に記録する（欠番にしない——docs/41 §9・docs/42 §4 の先例）。
- **欠番**：起票後に不要となった行は削除せず状態列を「取り下げ」として残す（ID 再利用禁止）。
- **出典 ID の修飾規則**：裸の `H-XX`＝docs/60 §4 棚卸しを指す（本書の調査基準——docs/42 §2.2「裸の H-XX＝docs/59 §4 由来・57-H-XX は修飾」と同型の慣行）。**`L-XX`＝抽出棚卸し**——§9.3 の網羅照合に出る「正典未記述領域」列挙の連番（Issue #8 棚卸しで抽出された領域群——§9.3 で定義）。統合元列で引用する際は「抽出棚卸し L-XX」と修飾する。

### 9.2 起票基準——何が要承認になるか

要承認に上げるもの（G-RL-12・P-RL-05・AGENTS.md）：

1. 面白さの根幹・公開方針に関わる決定（最終決定権はユーザー）
2. 正典値・承認値・正典節への変更を伴うもの（G-RL-11 の逆側——値の発生源への変更）
3. 複数案があり得る運用判断（LICENSE 選択・公開アルファ範囲・言語対応・章追加刻み・トレーラー構成・イベント形式・移植契機等——複数案比較＋推奨案つきで構造化）
4. Phase 0 制約を超える実施判断（公開・宣伝・**公開工程側の交渉**〔イベント運営・公開後の配信者関係〕の実施＝Phase 5 以降・ユーザー判断——**検証工程側の L3 配信者交渉は Phase 2・docs/41 の範囲**であり本書の起票対象外：§8.5）

要承認に上げないもの：判定手順の機械実施・表の追加更新・参照置換の実行（§10 の提案が承認された場合の転記作業）。

### 9.3 集約手順（統合時・運用時）

- **統合時**：各ユニットの起票出力（`.devin-work/issue8/u{n}_open_questions.md` またはユニット成果の open_questions 欄）を原票として本表へ転記し、統合元列に当該ユニットを記す。**U1〜U3 分は統合工程で追記する**——本節はそれを受ける書式として先に確定させ、U4 の起票は §9.4 に収録済み。重複は §9.1 の併合規則で処理。
- **統合時の網羅照合**：統合工程では、docs/60 §6 の未決想定枠（LICENSE 最終選択・アルファ収録範囲・言語対応範囲・解禁判定詳細・章追加刻み・トレーラー内容・サーバーイベント企画形式・移植評価契機）と、棚卸しで「正典未記述」とされた領域（**抽出棚卸し**——以下の連番：L-01 告知の媒体・タイミング／L-02 コミュニティ導線／L-03 サポート導線／L-04 版数体系／L-05 変更履歴規則／L-06 モデレーション方針／L-07 収益化方針の表明／L-08 ホットフィックス運用／L-09 公開ページ本文／L-10 GitHub Releases 運用／L-11 Issue #17 整備時期）が**いずれかのユニットの起票として現れているかを照合**する。欠落は統合工程で補充起票する——統合工程に起票ユニットは存在しないため `43-Q{n}` を暫定付番し（統合元列に「統合工程」を記す）、最終的な採番方式は 43-U4-Q8 の決裁に従う（不採用時は振り直し）。
- **運用時**：公開工程の進行で発生した新規論点は `43-Q{n}` で本表へ追記し、統合元列に検出経緯（工程 ID・出典節）を記す。
- **承認後**：承認済み行は推奨案どおり書き戻し先へ反映し、状態列を「承認済み（日付）」へ昇格。**一括承認**（「承認」の一言で全件推奨案どおり採用）を可能にするため各行は独立に成立させる（docs/40 §8／docs/41 §9／docs/42 §4 の慣行）。不採用・条件付きの場合は ID 指定で状態更新し、派生リスクは docs/42 §3.4 で行化する——本書ではリスク行を起票しない（G-RL-14）。
