## 3. 配布運用

> 本節の役割：公開チャネルごとの操作手順と版管理規則の設計。前提となる正典値は **D-3**（「配布は Modrinth＋CurseForge 両公開＋GitHub Releases を正とする」——docs/46 §7 承認済み）・**D-4**（modpack 収録条件5点）・**D-5**（公式軽量パック構想）。本節は手順の設計であり、公開操作そのものは Phase 5 以降・ユーザー判断で実施する（G-RL-01）。個々の段（限定招待→公開アルファ→正式→章追加）の定義と段間ゲートの判定基準は §1・§2 を参照——本節は「段が確定したあとの掲載操作」を規定する。

### 3.1 配布チャネル構成と役割分担

| チャネル | 役割 | 根拠 |
|---|---|---|
| **Modrinth** | 第一公開先・技術層向け。バージョン管理・依存宣言・.mrpack 配布の主基盤 | docs/46 §5「Modrinth＝第一公開先」 |
| **CurseForge** | 必須公開先。CF パック収録の前提・レンタルサーバー（ロリポップ等）ワンクリック導線の基盤——D-7 サーバーイベント主経路の土台（§5 へ接続） | docs/46 §5・§8（「サーバー導線を公開計画の柱に」）・docs/60 §1.1 |

**両公開の構造的必要条件**（docs/60 §1.1 引用）：CF パックは CF ホストの MOD のみ収録可、Modrinth パック（.mrpack）は参照 URL ホワイトリスト制で Modrinth 掲載外の MOD は入らない——片側のみの公開はもう片方のパック経路を失うため、**両プラットフォーム公開は必須**（D-3・G-RL-02）。3 チャネルの運用は排他ではなく同一バージョンの同時掲載を基本形とする。

**配布の単位**：本書が扱う配布物は3種——①本体 jar（Modrinth/CF/GitHub Releases の3系統）②公式軽量パック（§3.10・.mrpack/CF 両形式）③限定招待パッケージ（非公開配布——docs/41 §2.5 の運用に従属し本書は対象外）。③以外は全て §4.5 の公開前ゲートの対象。

**リポジトリの公開時期**：GitHub Releases を「正のビルド置き場」として運用するにはリポジトリ公開が前提になる。公開時期は正典未記述のため要承認とする（**43-U2-Q8**・推奨＝公開アルファ掲載と同時——解禁判定正本〔41-U1-Q10：Modrinth 公開アルファ掲載を目安〕と同期させる／対立案＝リポジトリ非公開継続——ただし「正のビルド置き場」運用とソース公開の透明性を失う。書き戻し先＝本節 §3.1）。

### 3.5 バージョンチャネル運用（alpha/beta/release の使い分け）

両プラットフォームとも 3 段チャネルを持つ（Modrinth：`release`/`beta`/`alpha`、CF：Release/Beta/Alpha——docs/60 §1.1）。公開段階（§1）との対応を以下に固定する：

| 公開段階（§1） | 掲載チャネル | 規則 |
|---|---|---|
| L2 限定招待・L3 限定公開配信 | **プラットフォーム非掲載** | 招待パッケージは非公開配布（docs/41 §2.5——「D-5 構想の先行形」）。Modrinth/CF には一切上げない |
| 公開アルファ | `alpha` | 解禁判定の目安＝Modrinth 公開アルファ掲載（41-U1-Q10・41-U3-Q2——判定手順の正本は §2） |
| ベータ | `beta` | 章追加候補の安定化段・修正の事前検証に使用（§1 の段構成どおり） |
| 正式リリース・章追加リリース | `release` | 完成した塊のみを出す（TF 慣行——「不完全な領域を出さない」docs/60 §1.2）。章追加は完成した章単位で release 系列に載せる（P-RL-01） |

運用規則：
- **下位チャネルの内容にも未完領域を含めない**——alpha/beta は「段階の表示」であり、未完の章・壊れた領域を混ぜた掲載は行わない（docs/60 §1.2 の TF 慣行を規則化）。
- **チャネル昇格は §2 ゲート通過のみ**——release への昇格は段間ゲートの判定記録を公開実施票に添付する（P-RL-04）。
- **同一版のチャネル不一致を禁止**——Modrinth で `alpha` の版を CF で Release に出さない（両チャネルの版・段表示を一致させる）。
- **緊急修正（ホットフィックス）**：セーブ破壊・進行不能級の欠陥が公開後に発見された場合、**当該版数体系の最下位単位を上げた修正版**（43-U2-Q2 の採用体系に従う——案A 採用時は `build`）を同一チャネルへ掲載する。発火条件＝修正版の §4.5 ゲート通過（緊急時もゲートを省略しない——ゲートは公開品質の担保であり例外を設けない）。記録＝公開実施票に「緊急修正」として種別を付記し、changelog の「修正」欄で症状と対処を書く。掲載頻度・ペースの設計（定期リリースか随時か）は段構成・スケジュール側（§1/§8）に従属する。

### 3.6 版数体系（TF 型 major.minor.build 準拠の検討）

正典に版数規則の記述はなく（棚卸し L-04）、TF の慣行 `{major}.{minor}.{build}` は比較基準として提示されているのみ（docs/60 §1.2）。複数案を比較する：

| 案 | 体系 | 利点 | 欠点 |
|---|---|---|---|
| **A：TF 型（推奨）** | `{major}.{minor}.{build}`——MC バージョンごとに並行系統を維持。アルファ〜ベータ期は `major=0`（`0.y.z`）、正式を `1.0.0` 起点、章追加・コンテンツ追加＝`minor`、修正＝`build` | ベンチマーク作と同一体系（docs/60 §1.2）。章追加＝minor が P-RL-01「章の刻みで世界が育つ」と一致。MC 系統別並行管理が §7 移植評価の結果反映（移植時に新系統を別立て）と整合 | major/minor の意味付けは独自運用（semver ではない）——changelog で意味を説明する必要 |
| B：semver 標準形 | `{major}.{minor}.{patch}`＋jar 名へ MC 版付記 | 汎用・ツール親和 | semver の「破壊的変更＝major」が章追加の刻みと直結しない——章追加が major にならないよう運用注記が要る。実質 A の読み替えに近い |
| C：章番号連動形 | `major=章番号` | 「何章まで入っているか」が版数から読める | 終章到達後の保守更新・修正で体系が破綻。アルファ期の表現が不自然（0 章？） |

**推奨＝案A**（要承認 **43-U2-Q2**・書き戻し先＝本節 §3.6）。jar ファイル命名は `understory-{mc_version}-{mod_version}.jar` 形を推奨（MC 系統の識別はファイル名側に持たせる——実装上の命名は Phase 1 で確定）。MC バージョン系統は現行 1.21.1 固定（42-U3-Q2・G-RL-08）で並行系統は1系統のみ——移植評価（§7）の結果に連動して系統追加を判断する。

### 3.8 変更履歴（changelog）規則

正典に changelog 規則の記述なし（棚卸し L-05）——以下を規則として設計する：

- **掲載面**：全バージョンに changelog を必須付記。Modrinth・CF・GitHub Releases の3系統で**同一原文**を使い回す（正本＝GitHub Releases の本文——「正のビルド置き場」D-3 引用。配置手順は §3.4 工程3）。
- **分類**：`追加 / 修正 / 変更 / 既知の問題` の4分類に固定（分類の外在化——P-RL-06）。各項は1行で、版数・チャネルを見出しに明記。
- **ネタバレ規則**：changelog は公開物——P-RL-02（情報の順序設計）を適用する。章追加リリースの changelog には**章タイトルと追加の大枠**のみ書き、場所系列の網羅列挙・結末・核心要素（由来物の正体・没腐・切り抜き瞬間——docs/41 §2.1 除外条件②の延長）は書かない。粒度の境界判定は §6 の開示粒度表に従属する（本節は changelog を粒度表の適用対象として位置づける）。
- **言語**：**要承認 43-U2-Q3**——推奨＝公開アルファ期は日本語のみ（42-U2-Q1「スライス期は日本語のみ」の公開物への延長）・Phase 4 の英語版範囲確定を受けて英語併記へ移行。対立案＝公開アルファ期から日英併記（英語圏の早期到達——ただし英語版の範囲は Phase 4 確定の 42-U2-Q1 と衝突し訳出コストが先行するため非推奨）。書き戻し先＝本節 §3.8。
- **既知の問題の記載基準**：ユーザー体験に影響する未修正事項は列挙する（透明性＝modpack 収録条件の信頼材料）。内部用語（デバッグ ID 等）は書かず、症状と回避策を日本語で書く。

**版数・更新運用・掲載先の選択**：**要承認 43-U2-Q7**——推奨＝本体の release 掲載ごとに追随更新し、パック専用の版数体系は持たない（表記＝「本体版数＋パック通番」）。掲載先＝上記の両プラットフォーム modpack プロジェクト＋GitHub Releases 添付、初回掲載＝本体正式リリース時。対立案＝パック独自版数体系（本体版数との対応関係が判読しにくくなるため非推奨）／GitHub 配布のみ（modpack プロジェクトとして検索・導入されず D-5 の「ワンクリック導入」の効果を失うため非推奨）。書き戻し先＝本節 §3.10。収録依存の版はピン留めし、本体との整合確認済み組み合わせのみを配る（ワンクリック導入の再現性担保——P-RL-03）。

**用途接続**：サーバーイベント導入の一発化手段（P-RL-03 → §5 の配布単位）・レンタルサーバーワンクリック導線の載せ体（§3.3）・L3 招待パッケージの公開形（docs/41 §2.5＝D-5 先行形の、公開版への昇格）。

### 4.6 公開停止・撤退規則

**発火条件**（いずれも「公開を続けると法務・正典・安全に反する」事象——発動判断はユーザーのみ）：

| 発火事象 | 該当リスク行 | 動作 |
|---|---|---|
| 同梱素材の権利不整合・第三者からの正当な権利主張の発見 | R-23・台帳関連 | 当該版の掲載停止→素材差替版の準備 |
| EULA 抵触の判明・収益化関連の問題発生 | R-36・R-22 | R-22 は**内容評価せず即時エスカレーション**——即座に掲載停止を検討しユーザー判断を仰ぐ |
| プラットフォームポリシー変更による現行公開物の不適合 | R-33 | 影響範囲の特定→説明文/設定の修正で吸収できなければ掲載停止 |
| 重大技術欠陥（セーブ破壊級）で修正版の即時提供が不能 | （運用事象——リスク行への追加は docs/42 側判断） | 当該版の掲載停止＋公開ページへの既知問題明記 |

**誰が**：ユーザーが最終判断・操作を行う。Devin は状況整理・影響範囲の列挙・手順実行を補助（面白さ・公開方針の最終決定権＝ユーザー——G-RL-12）。

**操作手順**（プラットフォーム別）：
- Modrinth：当該バージョンを非公開化（プロジェクト自体は残す）。事態がプロジェクト全体に及ぶ場合のみプロジェクト非公開
- CurseForge：当該ファイルをアーカイブ/削除。全体停止時はページを非公開化
- GitHub Releases：当該リリースを削除または注記付きで保持（正のビルド置き場の記録性を優先——削除より注記を原則とする）
- 共通：公開ページ説明文の冒頭に状況注記・changelog に記録（§3.8 の「既知の問題」欄）・公開実施票に撤退記録

**再開条件**：原因除去＋§4.5 ゲート再通過＋ユーザーの再開判断。再開時は同じ掲載手順（§3.2/§3.3/§3.4）を新規発火として実施する。

**境界**：L2/L3 限定公開期の撤退・削除請求対応は docs/41 §2.6/§5.5 の権利枠組みの運用（録画削除請求への応諾等は docs/41 側正典）——本規則は**公開掲載物**（Modrinth/CF/GitHub Releases の掲載版・公式パック）のみを対象とする。
