### H-22 カスタムフォント基盤（font プロバイダ）

- **実現性評価：高** — font プロバイダはバニラ標準機構：`assets/<ns>/font/*.json` に provider 配列を登録し、テキストコンポーネントの `font` フィールドで参照切替する。provider 種別 `bitmap`/`ttf`/`space`/`unihex`/`reference` は docs/56 §1.7 が実在確認済み。方式自体は承認済み（本文・かすれ系＝`ttf` 推奨＋フォールバック `reference`〔18-U1-Q5/U4-8〕、幻想文字＝`ttf`＋58 字形 1 系統〔18-U4-Q10〕）——残る不確実性は書体選定・和文グリフ品質・コードポイント割当・豆腐検出手法の設計面のみで、API の実在リスクはない。
- **検証内容**：3 フォント ID を到達させる最小構成の PoC。
  1. **3 ID の登録**：`assets/understory/font/body.json`・`faded.json`・`cipher.json` をそれぞれ独立フォント ID として登録（正典の「`font/understory.json`」記述はアセット群の呼称として解釈——`font` フィールドで 3 系統を切り替えるには 3 ファイル必要）。`ttf` provider のパラメータ（`file`/`size`/`shift`/`oversample`）を確定。
  2. **テスト資産**：body＝選定候補の和文 ttf（条件＝SIL OFL 相当ライセンス・和文 2,000〜7,000 字形・UI 9〜12px 判読——docs/40 §4.5）。cipher＝58 字形の合成テスト ttf（既存書体を fontTools 系で再マップした検証用資産。実書体の制作は資産側 Issue の領域で、本検証は機構の到達のみ担う）。faded＝bitmap 変種または専用 ttf（方式は 57-U3-Q4 で確定してから着手）。
  3. **表示切替の疎通**：書物画面（H-27 と結合）・看板・ツールチップ・字幕の 4 表示系で `font` フィールド切替を確認。次元別スキン規則（現実＝バニラ既定／国＝`understory:body`——docs/18 §2.2.1）は次元判定フックの疎通に留め、判定基盤本体は H-15 系に依存。
  4. **言語ファイル登録**：`assets/understory/lang/ja_jp.json`（＋`en_us.json`）で字幕キー `subtitles.understory.<領域>.<主体>.<動作>` を登録して表示疎通（名称権威＝docs/19 §3.6 台帳、sounds.json 側は H-20）。
  5. **欠損字形（豆腐化）検出手順**（docs/18 §1.4 の要求）：クライアント側 `net.minecraft.client.gui.font`（`FontManager`/`FontSet`）の欠損グリフ判定で対象コードポイントを走査する開発用チェッカー＋対象全文字のグリッド描画テスト画面の二段構成。意図的欠損フォントで検出能を先に証明する。
  6. **読み込みコスト計測**：数千字形 ttf 登録時のフォントアトラス生成時間・初回描画遅延・VRAM 増分を計測（§7 測定規格に従う）。
- **合格ライン**：
  - 3 フォント ID が `font` フィールドで個別切替され、書物・看板・字幕・ツールチップの 4 系で各 1 文字列以上が描画される。
  - 対象文字集合（和文グリフ対象範囲＋ASCII）で missing glyph ゼロ——検出チェッカーの出力が「欠損 0 件」を出せること（チェッカー自体は意図的欠損で検出能力を先に証明）。
  - 日本語本文が UI 9〜12px で判読可能（docs/40 §4.5）。読み込み計測は実測値を docs/40 §4.5 へ書き戻す（暫定合格線：初回フォント読み込み 2 秒以内・VRAM 増分 64MB 以内——着地は実測・G-TV-12）。
  - `subtitles.understory.*` が ja_jp/en_us で解決される。
- **設計代替**：
  | 破綻点 | 代替 |
  |---|---|
  | 和文フル書体の制作/ライセンス困難 | かな＋頻出漢字サブセット、または PixelMplus 等オープン和文ピクセルフォント（docs/00 Phase1 表の既定代替） |
  | ttf の小サイズ判読不足 | `oversample`/`size` 調整 → 不調なら bitmap プロバイダ化 |
  | 書体系そのものの縮退 | `reference`→バニラ既定フォントへのフォールバック層（18 §1.4 承認済み構造） |
- **依存・前提**：18-U1-Q5/U4-8・18-U4-Q10・48/04 §2.2-2.3（58 字形の行列構造・ガラ識別基準——ガラ＝行列構造に収まらない形、共有層の刻印として全員同一内容）・docs/40 §4.5・docs/18 §2.2.1。コードポイント割当・本文書体・faded 方式は **57-U3-Q1/Q2/Q4 で確定してから PoC 着手**。
- **Phase 1 タスク化**：①テスト ttf 準備（和文候補＋58 字形合成）②3 ID 登録と切替描画 ③豆腐検出チェッカー＋グリッド画面 ④字幕キー登録 ⑤読み込み計測。①〜③がメカニズム成立の本体、④⑤は並行小粒度。
- **想定リスク/工数**：リスク＝和文書体のライセンス適合判定と小サイズ判読性（低〜中）。工数＝中（資産準備が本体、機構側は小）。

### H-25 JEI 連携（カスタムカテゴリ＋隠し制御）

- **実現性評価：高** — `mezz.jei:jei-1.21-neoforge-api`（compileOnly・blamejared maven）＋`@JeiPlugin`/`IModPlugin` の `registerCategories`（`IRecipeCategory`）と `onRuntimeAvailable(IJeiRuntime)`→`getRecipeManager()` の `hideRecipes`/`unhideRecipes` は JEI 本体の公開 API として実在（mezz/JustEnoughItems の `IRecipeManager` 実装で確認済み——docs/56 §1.7 が同経路を列挙）。カスタムカテゴリの実装は先行実績の多い標準工程。
- **検証内容**：
  1. **依存配線**：JEI api compileOnly＋本体 runtimeOnly。JEI は必須依存（D-1）——mods.toml `required` 宣言。
  2. **カスタムカテゴリ 2 系**：拾得鍛錬台の鍛錬変換（入力→真の姿）・名付けの台（白紙の名札＋没素材→名付き）を `IRecipeCategory` 実装（タイトル・背景・スロットレイアウト・`registerRecipeCatalysts` の触媒割当）。独自機構は疑似レシピオブジェクトとして供給（docs/32 §9「独自機構は JEI カテゴリの実装対象」）。
  3. **隠し制御の端到端**：招待状（デカいゴミ箱のクラフトレシピ）・没の由来品系を `hideRecipes` で既定非表示 → 返礼発火・初拾得の解禁トリガで `unhideRecipes`（解禁チャネル＝57-U3-Q5——実績付与をクライアントイベントへ橋渡し）。

- **合格ライン**：2 カテゴリが JEI に表示・対象レシピが既定非表示→解禁イベントで表示復帰・`/reload` 後も隠し状態維持・EMI ブリッジ環境でも同等表示・通常拾得物・鍛錬レシピは当初から全表示（18-U4-Q6「正体が物語の答えになる物に限定」の適合）。

### H-26 Patchouli book.json 構成（拾得図鑑）

- **実現性評価：中** — book.json＋categories/entries の JSON 構成・`patchouli:book` コンポーネントの書物割当・実績連動ロック解除は確立機構（docs/46 §3・docs/56 §1.7——1.21.1 以降 Patchouli は NeoForge のみで技術軌道とも一致）。**中評価の根拠は 2 点**：(a) 「あなたが捨てたもの」節はプレイヤー個別の動的記録で、静的 JSON エントリの標準構成では描けない——`IComponentProcessor`（`vazkii.patchouli.api`・テンプレ JSON の `processor` フィールドとして実在確認済み）の変数差し込み or カスタム頁型が必要だが、件数可変のリスト表現まで標準で届くかは未確認。(b) 未開放項を「綴じ目の空き（内容・場所を示さず存在のみ）」へ見せる外観カスタマイズが Patchouli 既定ロック表示で届くか未確認。

  6. **交付シーケンス接続**：予告頁交付（ノミ綴じ→図鑑挿入→語り再生→頁提示——U1-#1）の「開いた際の着地先」として、`openBookEntry` 系 API で新頁項への直接着地が開けるか。
- **合格ライン**：未導入環境で起動不変・導入環境で 8 節構成の図鑑が開く・実績トリガで項が綴じ込まれる・未開放項が「存在のみ可視」規格に届く（または到達点を記録）・「あなたが捨てたもの」節がプレイヤー別内容で表示される・予告頁項への着地オープンが動く・村報節が掲示板代替として機能する（内容は共有・器は個別——docs/18 §3.6/U2-N5）。

- **依存・前提**：18-U2-Q1（8 節確定）・D-2（soft-dep＝図鑑系のみ）・40-Q9（FB 端到端要件）・解禁チャネル＝57-U3-Q5・個別記憶データ＝H-15（個別層データ構造）・頁データ層は H-27 と共有スキーマ（docs/40 §4.7）。
- **Phase 1 タスク化**：①soft-dep 配線＋未導入起動確認 ②book.json＋8 節骨格 ③実績ロック端到端（1 項の綴じ込み）④動的節 processor 試作 ⑤アイテム→openBook＋着地指定 ⑥未開放項外観評価。③が写像成立の中間ゲート。

- **実現性評価：中** — jarJar 埋め込みは NeoGradle/ModDevGradle の標準機構（`jarJar` 依存設定＋version range 指定）。GeckoLib は `com.geckolib:geckolib-neoforge-<mc>:<v>`（cloudsmith maven `dl.cloudsmith.io/public/geckolib3/geckolib/maven/`）として loader 別配布が実在し、公式も jarJar 同梱を案内。ただし (a) 埋め込み jar が専用サーバー/クライアント双方で正しく発見され mods.toml の依存解決を通るか、(b) versionRange と宣言の正しい組合せ、(c) 埋め込み jar 内の mixin/サービスローダーのロード順——は本プロジェクトの MDG 構成では未確認の帯。
