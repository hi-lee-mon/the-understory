### H-01 次元生成方式

- **実現性評価：高**
  - 根拠（API 実在・先行実績、P-TV-03/05）：次元登録はデータパック駆動——`data/<ns>/dimension_type/`・`data/<ns>/dimension/`・`data/<ns>/worldgen/noise_settings/` の JSON 定義、NeoForge では `DatapackBuiltinEntriesProvider`＋`RegistrySetBuilder` で datagen 可能（NeoForge commit ad6bf94——docs/56 §1.1）。地形生成は `minecraft:noise` ジェネレータ＋noise_settings JSON（`noise_router`・`surface_rule`・`spawn_target`）。バイオームは `worldgen/biome` JSON＋`MultiNoiseBiomeSource`/`FixedBiomeSource`/`TheEndBiomeSource` 型の決定論的配置。先行実績＝Twilight Forest（`TFDimensionData.java`：固定時刻・座標スケール・minY・ambientLight を JSON 定義、`bootstrapStem` で LevelStem 生成——1.21.1 NeoForge 継続リリース中。docs/21 §2・docs/56 §1.1）。1.21 のチャンク生成は `ChunkGenerationTask`/`GeneratingChunkMap`/`GenerationChunkHolder` へ分離されほぼ非同期化（`ChunkPyramid` がステップ依存管理——docs/56 §1.1）。
- **検証内容（PoC 仕様——Phase 1 タスク）**：
  - 作るもの：国次元の最小骨格。①`dimension_type` JSON（国の環境値：ambientLight・天空光・天井有無・minY/height 等——環礁ごとの環境光・空演出の個別制御は次元タイプの単一固定値ではなく別機構で担う設計を確認、docs/40 §4.2）②`dimension` JSON（LevelStem＝`minecraft:noise` ジェネレータ＋バイオームソース）③`noise_settings` JSON（PoC 段では最小の地形輪郭——海と島の原型。環礁本体の実装方式は H-07 の選択に従属）④`worldgen/biome` JSON 1 バイオーム（決定論配置——`FixedBiomeSource` またはカスタム BiomeSource）。
  - 動かし方：NeoForge MDK（ModDevGradle）1.21.1 で datagen（`DatapackBuiltinEntriesProvider`）により JSON を生成→統合サーバーで新規ワールドを作成→`/execute in` で次元へ移動し地形生成を確認。
  - 測るもの：①次元が LevelStem として登録・生成される（ワールド新規作成でエラーなくチャンクが埋まる）②noise_settings で地形輪郭（海/陸の原型）を制御できるか③バイオーム配置の決定性（座標→バイオームが安定）④`dimension_type` 各フィールドが環境表現に効くか（ambientLight・天空光・effects の視認確認——環礁別の個別制御の土台確認）⑤1.21 の非同期チャンク生成パイプラインで自前 noise が詰まり・エラーなく動作するか（`chunk_generation_stats`/ログ観測）。
- **合格ライン**：①統合サーバーで次元が登録されチャンクがエラーなく生成される（生成エラーログゼロ・`chunk_generation_stats` 出力に異常なし）②docs/40 §4.9 ゲート要件「カスタム次元1バイオーム」の成立③`dimension_type` の環境フィールドが確認される。書き戻し：確認した dimension_type 値と noise_settings 骨格を docs/40 §4.2 基盤要件へ反映（G-TV-12）。環礁本体の地形方式・演出面（空・光の環礁別制御）は H-07・§6 H-10 に連携。
- **設計代替**：先行ゲートのため要件自体に代替なし（docs/40 §4.9「次元生成・転移骨格——成立しないと主題装置が潰れる」）。実装経路内の代替：①noise プリセット流用（floating_islands/caves 系 noise_settings を改造）②自前 density function 設計③コード型ジェネレータ（カスタム ChunkGenerator——環礁本体の方式選択＝H-07 に連動。次元骨格は宣言型 JSON で成立する）。
- **依存・前提**：ADR-0002（NeoForge/1.21.1/Java21・データ駆動ワールドジェン方針）・G-TV-02。docs/40 §4.2（1つのカスタムディメンション・環礁別環境制御要件）。転移骨格は H-03（§3）。環礁地形の方式は H-07。
- **Phase 1 タスク化**：①datagen 基盤（DatapackBuiltinEntriesProvider＋RegistrySetBuilder）構築（小）②dimension_type＋dimension＋biome＋noise_settings の最小 JSON 出力（小）③統合サーバーでの次元登録・地形生成確認（小）④dimension_type フィールド実験→環境値の決定（小〜中）。
- **想定リスク・工数**：リスク低（API 実在・TF 先例——実在性に疑義なし）。工数小（検証単位として最小級）。

### H-02 異物チャンク生成

- **実現性評価：中**
  - 根拠（P-TV-03/05）：生成4型のうち③地形依存埋没＋①固定テンプレ（異質パーツプール）は構造物/フィーチャ系で到達可能（docs/56 §1.2——structure/template_pool/processor_list JSON 三重構造・structure_set spread/concentric・完全固定は自前配置関数〔TF 先例〕）。ただし正典の生成要件にバニラ worldgen 外の要素を含む——①「**スポーンから一定距離圏内に1箇所は必ず生成**」はプレイヤー単位の保証であり worldgen 時間軸（ワールド生成時・共有）と食い違う②「**棄てが極まった場所に追加生成**」は実行時イベントトリガ（ゴミ箱投棄量・場所の追跡→閾値到達で生成）であり世界生成時配置ではない③生成自体は**個別層生成**（発見者のみ視認・16 §3.7・45/04 M-1）であり、見え方モデル（H-06・§4）に連動。既存チャンクへの後付け生成（on-demand 設置）の安定経路は未確認箇所 → **中**。
  - なお可視性の実現経路（パケット偽装/エンティティ化/初接触消滅）は §4 H-06 のカード——本カードは**生成（どう・どこに・いつ作るか）**を担い、両者は一体で検証する（docs/56 §4「可視性モデルと一体」・docs/40 §4.9）。
- **検証内容（PoC 仕様——Phase 1 タスク）**：
  - 正典要件（引用）：定義＝「世界に捨てられた地形」（ADR-0005・docs/11 §4・docs/32 §4.1）。発生頻度＝ワールドあたり数箇所＋全プレイヤーに1つは必ず近場（スポーンから一定距離圏内）に生成される保証＋「棄てが極まった場所」への追加生成（J5 承認・docs/32 §4.1）。大きさ＝数チャンク規模（規模帯 M——16 §2.4）。型バリエーション＝複数型の異質パーツプール（Far Lands 的崩れ・存在しないブロック柱・文字化け看板・色の剥がれた村等——16-U1-Q13 承認）。生成形＝③地形依存埋没＋①固定テンプレ異質部品（16 §3.7）。視認強度＝「気配〜示唆」に固定（U1-Q5——本カードの生成側では「地形の異質性＝造形が一次」を満たす形状を担保）。使用後＝残存・再入可能（16-U1-Q14——個別層生成のため他者に視認されず干渉しない）。内部ダンジョン化はしない。没腐との関係＝異物の周囲は没腐が濃い（docs/32 §4.3）。
  - 作るもの：異物の最小生成。①1型の異質地形パーツプール（埋没型の異質部品 nbt＋埋没構造——生成形③＋①の検証用最小セット）を feature/structure 化 ②配置トリガ3系統の実現形を検証：(a) **ワールド生成時の共有希少配置**（「ワールドあたり数箇所」——structure_set spread/concentric または自前配置関数で決定論的に配置）、(b) **個別層のスポーン圏内1箇所保証**（プレイヤーの join/初回探索時に圏内未配置なら生成——コード生成による既存チャンクへの後付け設置）、(c) **棄てが極まった場所への追加生成**（ゴミ箱投棄の量・場所を追跡→閾値到達で近傍に異物を生成するトリガ機構）。
  - 動かし方：複数シード・複数アカウント（統合サーバー＋LAN2 人最小形——P-TV-06）で (a)(b)(c) を各々発火させ、生成位置・規模・型・既存地形との整合を確認。
  - 測るもの：①スポーン圏内1箇所の生成保証が複数シード（推奨3〜5）で成立するか（docs/40 §5.2.1 E-9 へ直結）②型バリエーションプールからの選択が動作するか ③「棄てが極まった場所」の検出→追加生成のトリガが成立するか（閾値の実装値は検証で試行）④既存（生成済み）チャンクへの後付け生成が地形と整合するか（埋没感・境目の曖昧さ——③地形依存埋没の要件）⑤個別層生成との接続（H-06 の可視性モデル決定に応じた生成形が取れるか——発見者のみ視認なら個別生成、初接触消滅なら共有配置でよい）。
- **合格ライン**：①複数シードでスポーン圏内1箇所の生成保証を確認（docs/40 §5.2.1 E-9 の観測基盤を提供——実シード数・圏内距離の実装値は検証で確定して E-9 に記録）②棄て閾値トリガで追加生成が発火しエラーなくチャンクに設置される③型が複数パーツプールから構成され「数チャンク規模の異質地形」として識別できる（視認強度の検証自体は E-9/§4 側）④埋没感（地形との境目が曖昧）が生成段で出る。書き戻し：生成保証の検証方法と「棄てが極まった場所」検出の実装値を docs/32 §4.1・docs/40 §5.2.1 E-9・Issue #13 結果記録へ（G-TV-12）。
- **設計代替（複数案比較——要承認 57-U1-Q2）**：生成トリガの実現形を比較する。
  
  | 案 | 方式 | 内容 | 強み | 弱み |
  |---|---|---|---|---|
  | A | 全共有配置 | 全て worldgen（structure_set spread salt 固定等）でワールド生成時に配置。個別化は視認側（H-06）に全委譲 | 生成は決定的・単純。個別化ロジックを生成側に持たない | 「全プレイヤーに1つは必ず近場」の保証が worldgen 時間軸と食い違う（join したプレイヤー毎に既存チャンクへの後付けが必要になり得る）。個別層生成の正典（発見者のみ視認・実体は個別）と不整合——同一地点に複数者が「自分の異物」を持つ設計が困難 |
  | B | 全個別動的生成 | join/探索時にプレイヤー毎の圏内・棄て場所へコード生成 | 個別層正典（個別生成・発見者のみ）と完全整合。位置は柔軟 | worldgen 外の後付け生成（生成済みチャンクへの設置・非同期）の実装検証が必要。「ワールドあたり数箇所」の自然発生（共有の希少地形としての役割）を個別層だけで見せる設計は「世界が捨てた地形」の物語層に弱い |
  | C | **ハイブリッド（推奨）** | ①ワールド生成時の共有希少配置（structure_set/自前関数——「世界に捨てられた地形」として複数箇所）＋②個別層のスポーン圏内1箇所保証＋③棄て極まりの追加生成（後者2つはトリガ式コード生成） | 正典の3区分（ワールド数箇所・圏内1箇所保証・棄て追加）に直接対応。共有希少配置が「世界自体が捨てた地形」の物語を担保し、個別保証が発見体験を守る | (b)(c) はコード生成の検証が必要。可視性モデル（H-06）の決定に生成形が連動するため、§4 との同時設計が必須 |
  
  推奨案＝案C。理由：docs/32 §4.1 の確定値（発生頻度3区分・個別層生成）に最忠実で、共有配置の物語的役割（「世界が捨てた地形」が現実に点在する）と個別層の発見保証を分離して担保できる。なお可視性モデルの選択（H-06・§4）が「発見者のみ視認」以外に変わった場合、案A（全共有＋初接触消滅）に退ける——生成トリガの独立性を保つ設計にしておく（57-U1-Q2 へ）。
- **依存・前提**：H-06（§4——生成形は可視性モデルに連動）・H-12（§4——個別層生成ロジック）。docs/32 §4.1-4.3（生成ルール・導線・没腐関係）・docs/11 §4（異物の定義）・docs/16 §3.7（生成形・パーツプール・残存）・ADR-0005・G-TV-05/06。縁の地（小規模・安全・素材あり）は別構造（docs/32 §4.2 U2-B/U4-#4——型バリエーションの共通パーツプール運用のみ接続）。環礁本体（国側）の生成方式とは別層（異物は現実側）。
- **Phase 1 タスク化**：①異質パーツプール試作（埋没部品 nbt——Far Lands 的崩れ等の1型から）（中）②ワールド生成時配置トリガ（structure_set または自前関数）（中）③個別層の圏内保証トリガ（join/移動時のチェック→未配置なら生成）（中〜大——既存チャンクへの後付け設置の検証含む）④棄て極まり検出→追加生成トリガ（中）⑤H-06 可視性モデルとの接続確認（中——§4 担当との連携）。
- **想定リスク・工数**：リスク中（個別層の on-demand 地形生成はバニラ非対応——feature/structure 設置経路は実在するが既存チャンクへの設置・非同期性の検証が要。可視性モデル未決のため生成形に分岐あり）。工数中〜大。

### H-07 環礁本体生成方式（複数案比較・推奨案つき要承認）

- **実現性評価：中**
  - 根拠（P-TV-03/05）：地形生成は noise ジェネレータ＋noise_settings（`noise_router`/`surface_rule`/`spawn_target`——density function 群を自前設計 or プリセット流用）、バイオームは `worldgen/biome` JSON＋MultiNoise/Fixed/TheEnd 型の決定論的配置（docs/56 §1.1）。構造物配置は `worldgen/structure_set`（spread 型＝塩・間隔・分離度——salt 固定＋確定的 spacing で固定配置に近似可能／concentric 型＝同心円）、**完全固定は自前の配置関数**（TF 先例：major feature をチャンク座標に決定論配置——docs/56 §1.2）。TF は 1.21.1 NeoForge 継続リリース中で「構造はアンカー配置、地表はノイズ」型の現行先例が実在（docs/21 §2・docs/56 §1.1-1.2）。ただし本作固有の要件——**環礁群（島体・海・淀み空間を含む次元地形）をワールド固定の脚本レイアウトで立たせる**実現方式は未確認・性能未知数 → **中**。
  - docs/40 §9 手渡しどおり「環礁本体の生成方式の選択（正典未決——複数案の比較検証。docs/16 §2.4 の確定4型は構造物の生成方式であり、環礁本体は同 §2.4 語彙規約③により一覧表の独立行に立たない別層）」を本 Issue の成果として比較・推奨し、ユーザー承認を取る（G-TV-04）。

### H-09 没腐地形 processor

- **実現性評価：高**
